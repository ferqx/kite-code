# Agent Note: 父轮结束后的子结果交付

Status: implemented

## Problem

Desktop 的实际项目检查中，父轮结束约 26 秒后子 Agent 给出最终报告。原 carrier 已成功，结果邮件仍在父会话待接收。用户确认此时应在父会话出现一条具名输入并继续处理。[上下文与子结果决定](../architecture/2026-11-14-agent-context-and-completion-delivery.md)采用的默认只排队策略无法完成该交付。

## Decision

- 默认 Service 在可信权限装配中启用既有 Task 完成策略。合格报告在原父轮正常结束、会话空闲时通过已有邮箱事务开启唯一后续轮。显式可信宿主策略仍优先。
- 续轮核对原 Tool、角色和配置租约，以及当前工作区信任、权限和控制修订。已有排队用户输入优先。缺少续轮资格的报告保留在原邮箱，按现有检查点接收。
- Desktop 直接展示已提交后续轮的具名结果气泡。结果继续作为带原 child 来源的低信任内容进入父模型，普通协作消息保留原用途。

## Alternatives considered

- 继续将迟到报告排队到下次普通输入，会让本次项目检查停在进行中回复，用户需要额外发消息取回已完成报告。
- 客户端收到完成事件后自行发起输入，会绕开原结果的原子接纳和去重，将同一结果交给多个窗口竞争提交。
- 让子模型用普通消息补发完整结论，会产生两份报告，普通消息在父会话空闲时同样会排队。

## Consequences

合格的晚到报告会产生一次后续父模型调用。已保存的委派授权与回执继续用于原工作校验，旧报告无法借新默认值取得原来缺失的续轮资格。产品入口见[执行手册](../../../../docs/handbook/features/execution.md)，策略和回归见 [Service owner](../../../../apps/service/README.md#默认-task-的源码外资格)。

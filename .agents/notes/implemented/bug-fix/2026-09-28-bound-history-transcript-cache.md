# Agent Note: Bound repeated Session History projection during pagination

Status: implemented

## Problem

Native clients load a Session transcript through fixed-watermark protocol pages. The App Server previously rebuilt the complete durable transcript for every page before selecting records for that page. Long parent and child threads multiplied SQLite decoding and projection work during navigation; many independent threads could make other reads wait on the same process.

## Decision

The Service History adapter retains the first page's projected transcript for later requests carrying its fixed sequence watermark. The cache key includes the root or exact parent-child scope and Session ID. Every request resolves the current Session through the Store reader before a cache hit, including the parent-child lineage check. Store 14 advances a per-Session event generation on row inserts, updates, and deletes. An unbounded first request may reuse the projection only when that generation matches; older readers without a generation rescan. The first scan is bounded by the Session sequence observed before it. Replacing a cache key removes its prior version even if the new transcript exceeds the entry limit. Entries expire after 30 seconds and are bounded by 256 entries, 32 MiB estimated serialized bytes per entry, and 128 MiB estimated serialized bytes in total. The stdio carrier locates the next record by sequence in the already sorted transcript. A digest of projected records and recovery metadata identifies content across pages at the same sequence watermark. When a continuation supplies the digest, the carrier rejects a changed value; the current client discards the partial transcript and retries once from the first page. Older clients that omit the optional digest retain prior pagination behavior without cross-page rewrite detection. This makes replacement and eviction safe for the current client without retaining every old version.

## Alternatives considered

- Rebuild the complete transcript for each protocol page: this kept no retained memory but multiplied the full read and projection by the number of pages.
- Reuse the first page using only `lastSequence` or `updatedAt`: neither changes for every same-sequence event rewrite, so repeat navigation could show stale output.
- Keep an unbounded transcript cache: this reduced repeated work but allowed many long histories to retain uncontrolled memory.
- Project each page independently from a Store cursor: legacy ownership repair and transcript recovery metadata depend on facts across the full selected journal. That would require a different stateful projection contract and was not needed for this bounded fix.

## Consequences

Later pages and generation-stable repeat navigations avoid repeated journal scans while retaining fixed-watermark and scoped-read behavior. Cache eviction or a transcript above the entry limit falls back to the original full read, so very large histories can still be slow. A digest change causes at most one automatic full read retry; another change returns an error instead of mixed output. The byte limits estimate JSON payload size and do not cap actual JavaScript heap use. Store 14 requires a protected 13→14 migration and one Session-row update per event mutation. An in-memory diagnostic of 10,000 inserts measured about 1.5 µs added per event; it is not a production write-latency guarantee. The [Service carrier owner](../../../../apps/kite-service/docs/runtime-server-carrier.md) holds the current limits and behavior; [History tests](../../../../apps/kite-service/test/runtime-history-client.test.ts) cover reuse, same-watermark replacement, over-limit eviction, append bounds, and child lineage. The [100-pair SQLite qualification](../../../../apps/kite-service/test/isolated/history-100-pairs.test.ts) covers complete and warm reads for 100 root plus 100 child Sessions with queued Promise requests and a same-sequence rewrite; its timings do not establish parallel execution or Desktop navigation latency. The [carrier qualification](../../../../apps/kite-service/test/isolated/runtime-stdio-carrier.test.ts) covers bounded aggregate scheduling across five connections and 1100 History requests. The [protocol-chain stress test](../../../../apps/kite-service/test/isolated/history-protocol-100-pairs.test.ts) has also completed 1000 and 2000 parent-child pairs with explicit overload/retry and a concurrent Runtime query. These synthetic results do not establish an unlimited capacity or a real Desktop navigation latency SLO.

# Agent Note: 用户引导与 Agent 邮箱的统一接收

Status: implemented

2026-10-28，[前台批次收尾决定](2026-10-28-guidance-after-foreground-tools.md)部分替代下述用户引导使未派发 Tool／审批失效的行为：原 Tool 队列先收尾，独立引导随后进入模型。本文的统一邮箱、来源、权限、去重和续跑理由继续适用。

## Problem

用户引导、普通 Agent 邮件和子 Agent 最终结果已经进入同一父会话，但 Runtime 分别扫描用户输入、完成报告和邮箱。结果与普通邮件的接收、去重和观察水位由不同路径负责，容易让一个结果被重复发布，或在父轮活动与结束的边界重复续跑。

后续真实窗口验证还发现普通邮件的完整正文只在模型上下文展开，公开历史把内部占位当用户消息，丢失发送者／正文并拆开同一 Run 的处理过程。

## Decision

参考 Codex 的 InputQueue，保留用户输入入口与 Agent 通信来源，在一个串行接收检查点汇合。普通子 Agent 消息与最终结果复用现有邮箱，用户明确排队的输入继续遵守原前驱与顺序；不引入通用目标策略。

新的 `agent_completion` 沿原唯一 `job.report`／`job.report.continue` Command 封存内部邮箱版本和目标列，成为同一邮箱中的结果项。沿用原结果 ID、父会话准入回执和 Run origin，不建立第二条 accepted 记录。新结果从邮箱消费，旧未标记报告与非 Agent Job 保留原协议。结果仍以唯一 result Source 发布，物理 Message 与 Source 的接收身份明确区分。

活动父轮在安全检查点接入本轮；父轮结束后由已有调度资格、原配置与当前权限决定是否续跑。原子事务决定接收 Run、发布 Source 和回执，多结果可以共用一轮。普通 QueueOnly 邮件不自行启动空闲接收者。用户引导保留未派发决定失效语义，Agent 数据不取得这项权力或工具批准。

普通邮件的公开展示由 Runtime 只读验证原接收回执和原 Artifact，返回 system 消息、完整正文及 `agentMessage` 来源元数据。Native 复用原 MessageItem，在实际接收 Run 的同一处理过程中显示；不写第二份实体正文，不改变模型上下文或最终结果的 idle 气泡资格。

## Alternatives considered

- 为三类输入建立统一目标策略和新的总队列，会重复现有用户队列与邮箱的职责；用户明确要求沿 Codex 的接收结构收敛，保留原接口校验。
- 为结果另建 `agent.message`，再创建父会话准入记录，会增加两份身份、状态与恢复证明。直接把原结果 Command 作为 typed 邮箱项可以复用现有精确来源与 Run origin。
- 仅把三个消费函数放进包装函数，仍然保留新结果的独立 pending 扫描，无法收敛接收 owner。新结果应只经过邮箱接收入口。
- 把结果正文同时写入普通 Message 和 Source，会让模型重复读取正文；展示继续引用原 Source，不额外投递。
- 只在前端替换内部占位文案或按正文猜作者，无法证明发送者，也仍会把收件当用户输入。用虚拟 Tool 表示邮件则会制造不存在的执行身份；公开的普通邮件采用独立来源元数据并保留原过程归属。

## Verification

真实 Runtime／SQLite 回归证明活动轮接收、空闲条件续跑、用户输入优先、普通邮件不主动续跑、来源和权限区分，以及消息／Source／续跑轮次的去重。Source 和回执故障整体回滚，提交后丢响应查回同一结果；冷读取不写入、不启动模型。既有结果气泡只反映真实 idle 续跑，活动接纳在结束或重开后不补气泡。

## Consequences

结果的失败状态不等于普通邮件 sender 未成功，两者分别核实。结果的 Source ID 不写入物理 Message 外键；观察水位覆盖两种发布类型。旧报告恢复、continuation 资格和配置 lease 保留，缺失或损坏的邮箱标记不能退回另一条投递路径。协议封装痕迹与有效版本分开检测，旧无标记记录仍可列出；真实 SQLite 破坏证明的反例核零 Source／Run，错误轮次重收保留原回执。

公开普通邮件来源必须核原 Command、发送 Tool 成功事实、父子关系、接收 Message／Run／selection 与 Artifact 引用；来源损坏明确不可读且不推断作者，正文读取失败保留已验证发送者并标为未完整交付。公开读取不增加投递、Run、Source 或授权。

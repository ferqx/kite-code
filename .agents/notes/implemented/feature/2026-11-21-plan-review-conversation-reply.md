# Agent Note: 计划审阅与原任务用户消息

Status: implemented

## Problem

普通提示词输入同时承担计划答复会混淆审阅和会话引导。用户确认正文留在会话消息中，审阅动作放在原提示词输入框的位置。「开始实施此计划」及计划的文字回复要进入同一原任务的用户消息。

## Decision

会话内的计划文档使用真实版号和正文预览，全文沿原消息展开。会话底部的专用面板承载实施、跳过和文字回复。实施提交当前版本的 `approve`，同时保存固定用户消息。跳过提交 `deny`。专用编辑器提交 `revise` 和原文，模型可据此回答问题或修订。根会话待审时隐藏普通输入和队列引导入口，审阅结束后恢复。计划答复通过 `asUserMessage` 选择在同一事务保存 `feedback` 作为原 Run 用户消息。

## Alternatives considered

- 单独发后续输入与审阅答复会形成两个独立回执。断线后可能只提交其中一个，也可能把实施提示送到下一轮。采用一个已绑定审阅的命令保存两个事实。
- 主输入复用为审阅意见入口容易让用户误判文字的去向。专用面板在同一位置明确文字的去向，三种动作共用原提交门禁。
- 操作放在计划卡末尾时，长计划的展开和滚动会改变操作位置。放在会话底部可边读正文边答复。

## Consequences

重试核对原命令，保存过的决定只产生一条用户消息。带意见的旧答复继续以历史意见显示。计划正文验证、决定接纳和执行条件沿原身份核对。审阅结束后恢复原主草稿，审阅草稿按原交互修订交付。暖窗历史在同一视图复用已经完整核验的原文和展开状态，冷读取沿原附件证明。此决定接续[早期桌面计划审阅](2026-11-21-native-plan-review-composer.md)的原文放置、原版本绑定及回执保护。页面归 [Desktop owner](../../../../apps/desktop/README.md#native-计划入口与完整审核)。

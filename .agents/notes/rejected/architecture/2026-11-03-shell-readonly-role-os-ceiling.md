# Agent Note: 只读角色的命令限制与 OS 执行上限

Status: rejected — OS 禁写／禁网上限仍不采用；命令门禁部分已由后续决定替代。

## Problem

只读子 Agent 当前依靠固定工具集合与有限 Shell 分类限制行为，底层仍使用普通可写执行范围。分类遗漏会同时影响免审和角色门禁，模型提示词无法保护未进入审核的调用。另一方面，按程序名称猜测任意脚本的全部文件／网络效果，会增加误拦，也不能提供完整保证。

用户于2026-11-03确认：保留现有只读命令限制，同时规划 OS 级禁止业务写入／联网的兜底。普通请求批准、自动审核与完全访问的产品含义保持。

## Rejection rationale

用户于2026-11-03重新评估后选择最小调整，不实施角色专属 OS 降权。已复现的参数分类、身份、期限摘要、审核指引及能力描述归属问题已修复，原三模式、只读工具／命令门禁、父子范围与普通平台沙箱继续生效。独立 OS 只读属于额外保证，不是本次修复的前置条件；当前产品明确保留分类遗漏风险，不宣称业务进程在该情况下仍无法写入或联网。

本决定不放宽任何已有角色门禁，也不把普通沙箱删除或扩大。以下保留原提案的目标、备选和风险，用于解释未采用的范围；它们不再是实施要求。当前实现和验证归[权限 owner](../../../../packages/agent/src/permissions/README.md)与[Service owner](../../../../apps/service/README.md#默认-shell-装配)。

后续[任务权限继承决定](../../implemented/architecture/2026-11-03-readonly-task-role-permission-inheritance.md)仅替代上述“保留命令门禁”部分：只读作为任务指导，Shell 继承普通权限与沙箱，不再使用角色专属命令表。不增加角色 OS 上限的取舍仍有效；前文与下述提案保留当时理由，不代表当前存在命令硬门禁。

## Proposal

只读角色同时受到命令门禁与 OS 约束；业务 Shell 进程树无普通文件写入和网络能力，Full、人工批准、模型批准及旧会话授权均不能移除。宿主模型请求、输出持久化与监督保留各自原边界。

可信角色事实沿父子配置、审核材料、准确授权和最终 Job 证明传递；适配器消费最终有效限制。没有对应平台能力时只读 Shell 不可用，不回退普通进程，结构化读取继续可用。普通 Shell 保持按调用申请 none／internet，网络授权覆盖整次进程树，不宣称域名级限制。

原实施计划已随本提案取消而移除；已交付事实与验证保留在负责模块，原平台资格约束仍由[Jobs owner](../../../../packages/agent/src/jobs/README.md)维护。原[单次范围决定](../../implemented/architecture/2026-10-11-shell-per-call-permission-scopes.md)关于普通三模式、文件／网络独立授权、最终证明和禁止扩权重放的理由仍适用；本提案增加只读角色的 OS 上限，不替代普通模式合同。

## Alternatives considered

- 只修分类与审核指引：是必要修复，但仍由同一个分类结果保护免审与只读角色，不能兜底后续遗漏。
- 通过 OS 只读后开放任意 Shell：用户选择保留现有命令范围，不以新沙箱扩大工具行为。
- 持续增加可识别联网程序名称：无法覆盖脚本、hooks 和后代；不能作为网络授权来源。
- 所有 Shell 均增加人工确认：改变已确认模式含义，且确认本身不能兑现 OS 只读保证。
- 用离线环境提示替代 OS 禁网：不能约束不遵循提示的进程，不满足用户确认的强保证。

## Acceptance criteria

命令门禁正反例、独立原生禁写／禁网、正常读取／输出／取消、Full 与父子交集、动态模式、准确授权复用和冷恢复均按方案分别取证。只测策略 allowed／denied、受控模型或其他平台不能宣称 OS 验收通过。

## Risks

Windows 当前普通离线仅提供环境提示，不能直接宣称具备严格只读 Shell。平台能力不足时会减少只读角色的 Shell 可用性，必须准确说明，不能静默降级。native 表达能力须先核实；若涉及工具定义或协议版本升级，须先取得具体升级确认。本提案尚未实施，也不代替原平台或发布资格。

# 候选证据与取舍

用于跨层或大型候选；普通局部重复不必逐项展开。记录当前 owner、实际生产者与消费者、拟删除的维护面、保留的胶水，以及最强的保留理由。把结论分成“行为保持的冗余”“需要明确收窄产品或公开契约”“受保护或证据不足”，不要把后二者伪装成已授权重构。

## 找到完整效果路径

从创建值或事件的入口，追踪转发、存储、执行者到可观察结果。只有声明、序列化分支或测试，不证明功能真的发生；有调用者也不证明其参数被下游兑现。查符号及其读写、事件名、配置键、wire 字符串、构造点和实际运行入口。对公开扩展点还要核对外部消费者契约，不能把仓库内零调用等同于不可达。

比较多个状态或表示时，问每个区别让哪个消费者采取不同动作。可在使用时从权威值推导的缓存、重复通知和同步账本是候选，但要先明确读取时刻、持久性和独立写入者；一个展示端不读取某事件，不代表该事件对恢复或其他消费者无用。检查只验证自身刚执行的同一变更，通常弱于比较独立产生、可能分歧的事实；不能仅为删门禁而忽略后者。

## 判断真正消失的复杂度

对防御性拷贝、冻结、验证和回调捕获，标出值从哪里来、接下来归谁、是否穿过文件、网络、进程或不可信输入边界。对异步代码，给每个 flag、Promise、取消路径和 disposer 找到独立 owner 与状态转换；只有表达同一事实的机制才可合并，保留不同 owner 间必要的发布、回滚、终态仲裁和静默收尾。

比较变更前后的完整成本：公开 API、配置、状态、依赖、构建入口、测试、文档，以及替换后仍需的适配代码。引入依赖时先核对现有依赖和平台内置能力，验证库是否覆盖本仓库的界限、取消、失败与打包语义；需要重新实现核心边界就不算净精简。若方案仅让行为更窄，明示失去的能力并按用户授权处理，不能用“代码更少”替代行为决定。

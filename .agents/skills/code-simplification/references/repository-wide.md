# 全仓覆盖与验收

整仓精简的目标是在用户指定的完整范围内找出有证据的冗余，并实施可安全完成的改动。它不意味着逐行改写，也不以删减行数或候选数量判定完成。

## 建立覆盖范围

先根据 workspace 清单、构建与运行入口列出待审查的 apps、packages、脚本和测试归属。对每个模块核对 owner 文档、公开出口、主要运行链和测试，再记录“已审查且无安全候选”“已实施”“因契约保留”或“证据不足”。范围很广时可按独立领域并行审查，但由主 Agent 合并证据；没有覆盖到的模块必须明确列出，不能用抽样结论代表全仓。先看生产代码体量大、生命周期或重复状态集中的模块，不要找到首批无用符号就结束调查。

搜索静态 import 只是候选发现手段。删除文件、导出或资源前，还要检查路径别名、包 subpath、动态加载、worker/子进程入口、路由与注册、构建和发布清单、文档与测试引用；生成目录和外部插件入口也可能提供真实消费者。测试专用文件也可能保存安全或兼容证据；不能仅凭生产调用图不可达而删除。若现行产品文档承诺的行为与代码不符，分别记录预期、实际、影响和证据；只有独立的已确认需求能证明文档有误时才修正文档，否则保留产品承诺并标明待决，不以当前实现自动覆盖预期。

## 分批实施与验证

将互不依赖的候选组织成可独立审查的改动，优先完成行为保持且有明确消费者证据的部分。开始前记录相关测试和强制门禁的基线；改动后按受影响的模块运行测试、类型/构建与边界检查。基线测试若在首个失败处停止，核对该失败与改动的关系，并记录哪些后续测试实际未运行；可针对本次改动补足必要验证，但不能把未运行部分记为通过。对基线失败或本次回归分别说明证据，不以更改断言掩盖失败。

交付时分别报告覆盖范围、实际改动、保留候选的理由、通过的验证、失败及未运行的验证。只有请求范围已按上述方式核对、可安全实施的候选已处理、必要验证可支持结果时，才称整仓精简完成；否则准确说明已完成的子范围和剩余阻塞。保留公开契约、安全、迁移或恢复机制时，不将其误报为精简遗漏。

# Persistent Run requirement registration owner

`ReadContext/ConditionReadContext.readRunExecutionSafety(runId)` observes the exact original Store/subject/Session/Run and its persistent execution closure, including runless descendants and actual child groups. A consistent snapshot returns a canonical revision, `unconfirmed`, the Host's actual `excludedExecutionId` and bounded `unconfirmedExecutionIds`; those IDs are observed facts and confer no cancellation or recovery authority. Planned/active or unknown Tool/Job effects cannot confer a safe waiver. The Host fixes an exclusion only to its own actual Tool boundary and still traverses that Tool's descendants; a Job read excludes nothing. It automatically captures at most one `executionSafetyReads` entry for a requirement, and the final transaction recomputes the same closure and exact revision/boolean. Evaluators cannot choose a different excluded execution or supply safety prose as authority. More than the finite 4096-execution observation boundary is unavailable, rather than falsely safe; this does not add a Run execution quota or make unconstrained ordinary conversation require a safety read.

A satisfied dispatch condition for an actual planned Job may retain `unconfirmed:true` with no exclusion: the Job and its real parent work can themselves be in the observed closure. The evaluator must check the precise allowed work relationship; the final dispatch transaction and that Job's approval acceptance verify the unchanged whole closure and actual Job membership. Completion, waiver and informational acceptance still require a clear closure. A changed third execution, parent state or revision rejects the old proof. [Actual Store tests](../../../../test/isolated/storage/execution-safety.test.ts) and [Host tests](../../../../test/isolated/execution/condition-context.test.ts) exercise this generic second consumer, automatic capture, scope, changed facts and completion/waiver refusal without Skill state in Core.

`registerRunRequirements` is a finite owner-only transaction for the actual active Run. The original Store, root group owner/generation, original command cancellation, child carrier and ancestor stop/delete boundaries are checked before writing. Registration appends obligations and has no remove, replace or downgrade operation. An exact registration retry performs no event or record write; concurrent identical submissions converge on one obligation. If the business record later changes revision or origin, the exact retry returns only its already-sealed historical obligation. It cannot refresh that binding; final dispatch/completion still rejects stale provenance or evidence, and a new obligation cannot acquire invalid record qualification.

An obligation key is extensionId + requirementId + exact Session/Run + optional actual Execution/attempt. Its definitionVersion, recordKey, record revision and dispatch/completion/both phase are immutable bindings. Another scope can add a separate obligation but cannot remove the existing one. Each newly registered ref must name the actual current Run and Session. Optional executionId must exist in that Run under the same owner generation and Store; attempt must match its real attempt and cannot appear without an execution ID. Unknown-effect executions cannot confer executable qualification. Child registration preserves inherited parent refs unchanged and only appends new child-Run refs.

The record must exist in the extension's Session namespace with the exact revision and executable origin from the current Store. The Store seals originStoreId from that actual record; caller omission never supplies provenance, and a different caller claim is rejected. Definition version and record contentVersion are independent owner contracts; registration does not assume they are equal or inspect business values to infer authority. Cross-restored or unmarked records cannot be relabeled through registration. Final dispatch/completion and informational acceptance require sealed origin and verify it against the current record and Store. A ref injected without a seal cannot grant execution and cannot be upgraded through an exact registration retry. New storage has no compatibility authority path for old unsealed obligations.

At most 64 total refs and 32 KiB of canonical JSON may be retained. The Run requirements update and run.requirements_registered event commit together. A failed event/transaction rolls back the entire addition. Hosts must use returned Run.requirements for subsequent evaluations because those refs contain the Store's sealed provenance. Actual business evaluators remain outside SQL transactions; the Store does not invoke a Model, Tool, plugin or second workflow.

Existing Job creation freezes the current parent Run refs. A later registration affects future Run gates but cannot silently change that already-created Job snapshot. Real temporary SQLite tests in test/isolated/storage/requirements.test.ts register records and refs through public Store methods, then exercise missing/stale evaluation rejection, immutable bindings, simultaneous retries, owner/Store/scope/cancel and byte bounds, real trigger rollback, readonly reopening, restored origin, unknown execution, child inheritance and Job snapshot independence. No fabricated requirements are inserted with SQL.

`applyJobReport` 在核实准确原父 Run、成功 source、已知 carrier/result revision、afterTurn、selection 和取消边界的同一事务中，把父 Run 的 requirements 原样复制到新报告 Run。它不撤回原 refs，也不调用业务 initializer 重登记其他 Run 的义务；空 initializer 保留继承引用，普通 registration 仍只允许新增当前 Run refs。报告的实际 Model/Tool/完成继续核这些原 refs 的全部 record read-set，旧 head revision 或缺条件不能取得派发资格。[真实原报告 Store 测试](../../../../test/isolated/recovery/job-report-resume-store.test.ts)通过公开 metadata/record/requirement API 建立原义务，验证冷 report 继承、空初始化保留、外国 refs 拒绝、head revision 漂移零事件/派发和同报告幂等，未用 SQL 伪造义务。

Evaluator `recordReads` is a finite final-transaction CAS read set, scoped implicitly to its requirement's extension and Session. At most 64 entries and 32 KiB of canonical JSON are allowed; duplicate keys, unknown scope/authority fields, invalid revision/origin claims and outcomes other than satisfied/waived cannot qualify a commit. Present related records must retain their exact revision and executable original Store; a recorded absence must remain absent. Evidence prose does not substitute for these facts. Real public Store tests in test/isolated/storage/requirement-read-set.test.ts use an accepted approval, actual dispatched record writers and persistent registration: changing plan/approval/evidence after evaluation rejects dispatch or completion without events, accurate fresh reads succeed, unrelated writes are harmless, and namespace/absence/origin claims cannot grant authority. This verifies the Store boundary for declared dependencies; business evaluators still own selecting all necessary plan, approval, validation and waiver reads.

`initializeRunRecord` is a finite metadata-only initializer for the actual active Run before its first planned Execution. It checks the original Store/command, root owner generation, child carrier and ancestor stop boundaries, selects only an extension in the sealed Run manifest, and requires a nonempty `run/<actualRunId>/...` key. Values are bounded to 32 KiB canonical JSON and records to 64 across that Run's extension namespaces; callers cannot set executable authority or replace existing content/version/type. An exact retry adds no event; retained initializer access closes as soon as any actual Execution is planned. Real tests in `test/isolated/storage/requirement-initialization.test.ts` cover these limits and gates, child initialization, event-trigger rollback, readonly reopening and foreign origin rejection without relabeling. Initializer results retain the same explicit `forkProvenance` projection as later namespace reads (null for a new record); exact retry and readonly reopening return the same record shape. SQL is used only for deliberate trigger/provenance fault injection, never to fabricate initializer permission or executable qualification.

Operation result declarations are sealed with the original carrier in the same ensure transaction: namespace/schema come from the captured host Extension, while Store, subject, actual parent Run/execution, original command/root work, selection and carrier key come from committed facts. A bounded captured schema validator is prepared before the write transaction; SQL validates only the finite generated metadata. Exact replay cannot alter disposition/schema or add a missing obligation. These refs explicitly select the captured Extension conditions provider; removing a factory cannot silently remove persisted refs or fall back to another evaluator. Task settlement requirements concern accurate known terminal acceptance, not verification success. `setRunResultWait` reuses waiting_execution with at most 64 exact registered pending carrier IDs; it cannot copy child lifecycle authority or revive a terminal Run. Real tests in test/isolated/storage/result-requirements.test.ts demonstrate atomic trigger rollback, schema rejection without residual child state, immutable replay and status-only unknown diagnostic gates.


自动 mutation 义务复用现有 extension_record：Run 级 immutable policy/ref 与分页 intent、准确 Execution settlement、check attempt 和 CAS head 分开保存。`registerMutationIntent` 在派发前核实真实 Store/owner/Run/定义/父链；最终 markDispatching 再次要求对应 intent。`finishExecution` 同一事务记录真实 terminal 与 settlement/head，不由 after-hook 补写。`commitMutationCheck` 必须来自准确已派发 checker，核实当前 head、原 target、顺序和实际终态；旧 callback 不可覆盖后序 mutation。`superseded` 仅对已知成功事实生效，后序证明从相同 namespace/Run/Store 的真实 intent/Execution/receipt 派生并在 commit 再核实，不从调用者 evidence 自报选择新目标；它不等于旧文件 hash 检查 passed。记录格式/版本/origin 不符、sequence 溢出、父链不明与 unknown 均拒绝资格。事实页从持久 intent 和 execution 读取，不依赖可裁剪通知。具体装配、同 Loop continuation 与证据见[Planning owner](../../../business/planning/README.md)及[真实测试](../../../../test/isolated/business/automatic-validation.test.ts)。

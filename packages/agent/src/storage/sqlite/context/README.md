# Context selection and result delivery Store owner

`selectContext` is a public root-Session command with original subject, Store identity, exact current selection and committed complete message boundary CAS. It rejects an active Run, planned/dispatched/running execution or unconfirmed unknown side effect anywhere in the execution group. A boundary must already belong to the current selected history and preserve assistant/tool call pairs. The immutable new selection retains the intersection of the old selected prefix and requested boundary, plus future messages after the transaction's sequence high water. A later rewind cannot silently restore an excluded branch. Raw message history remains readable.

The same transaction changes the Session pointer, suppresses old pending Job delivery as context_rewound, rejects all previously accepted work in the group and persists the context Command receipt/event. Generic work admission records its selection; final startRun also verifies that binding. New explicit commands admitted after selection may start normally. There is no automatic restart, model call, Job retry or hidden continuation in this module.

`consumeJobResult` is an owner checkpoint transaction for an exact pending Job, result revision, original Store, target Session and current selection. A child Loop may consume its own delivery under the root group owner; its original subject is derived through child.start, the actual carrier/parent/root chain, and the carrier must remain active. Ancestor cancellation, deletion and stop boundaries are rechecked; public select/include remain root-only. During an active Run the caller must identify that exact Run; idle consumption cannot pretend to attach to a Run. Cancellation/root stop and changed selection forbid automatic consumption. A consumed reference, delivery status and internal command receipt commit together. Retry returns the original source without new events or model work.

`includeResult` 是原主体对 root Session 的显式 result.include 命令，保留准确 execution/revision/origin，包括显式 restore 后原 Store 的历史结果。idle 时不带 targetRunId，仅登记后续来源，不创建 Run 或派发；同一选择下已有来源复用原 source ID。活动时必须给准确 targetRunId，原 Run、selection 与 rootWork 在受理及应用时复核；回执先为 accepted/result_queued，来源尚未 selected/resultAcceptance。Core 在同一 steer checkpoint 按服务端顺序应用为低信任结果 source；只收束未派发决定及其审批，已派发请求保持原事实。派发与完成事务的 input_pending 关闭受理竞态。显式选入不把 suppressed 改回 pending，也不重放原 Tool/Job。

活动来源在应用事务中分配新的 Session 发布序号；受理时取得的旧 upperSeq 不会在后续分页突然包含该来源。原 source ID 和命令意图保持不变，重复应用不再分配序号或事件。

Selection metadata and immutable result references reuse context_snapshot. References point to the original terminal execution fact rather than duplicating large result bodies or creating standalone Provider tool-result messages. Core formats result sources with their actual source IDs. Context selection lookup uses the real Drizzle schema/query path; transactions and bounded selection queries use explicit prepared SQLite statements.

`getSelectedContext` is a consistent read snapshot. It returns the current selection, complete selected messages, selected result sources and a Session sequence high water. A caller paginating must keep contextSelectionId and upperSeq fixed and exhaust both independent message/source cursors. New later messages and references belong to the next snapshot. Defaults are 50 messages, 50 sources and 1 MiB body budget, with finite maxima of 200/100/8 MiB. An individual fact exceeding the selected budget produces context_item_too_large instead of falsely claiming a complete truncated result. Raw listMessages remains history-only.

`listPendingJobResults` is a pure read using actual execution.finished cursors persisted as execution.completed_cursor in the same terminal transaction. Pending delivery remains authoritative when disposable notification rows are trimmed; listing does not depend on their continued existence. It returns at most 100 lean terminal pending references for the exact delivery target Session. Freeze upperCursor at highWaterCursor and advance afterCursor by completion facts, never execution IDs; a lower ID completing later remains visible at the next checkpoint. snapshotCursor reports the read's actual Store high water. Wrong Store, invalid INT64 cursor or cursor ahead of committed history rejects without writes. Consumption remains a separate owner transaction, so concurrent consumers must check its final receipt.

Real temporary SQLite tests in test/isolated/context/store.test.ts cover before/after startup suppression, immutable source provenance, repeated rewind, retained raw history, whole-group child/unknown qualification, public/owner scope checks, real trigger rollback for selection/include/consume, restored Store origin, read-only reopen, two-Worker completion pagination after notification pruning, child-owned consumption, JSON-expanded legal input budgets and Provider call pairing. compression 和完整恢复资格仍不由此基础声明完成；after_turn 由独立因果汇报路径维护。

[active-include.test.ts](../../../../test/isolated/context/active-include.test.ts) 以真实 Core/SQLite、已派发固定 Model 与准确审批卡证明旧请求不变、下一 Model 的唯一完整低信任 source、原 Tool 零重放和精确取消。store.test.ts 的真实触发器覆盖应用来源、消息、superseded 状态与回执整体回滚；旧 Run 目标不漂移，尚未应用的引用不构成 resultAcceptance。

An exact registered operation-result completion ref may consume known terminal status suppressed solely by execution_cancel while its original parent Run/current selection/root work remain valid. That narrow path preserves suppressed delivery and includes only a status-only settlement source; ordinary suppressed Jobs, root stop/delete and rewound context remain ineligible. The separate requiredDiagnostic path accepts only an exact outcome_unknown fact as one status-only low-trust diagnosis source: it leaves delivery unchanged, is excluded from Execution.resultAcceptance and never satisfies the obligation. Original command IDs/revisions make both retries idempotent. Runtime does not route required unknown facts through ordinary full-body automatic delivery. Real result-requirements Store tests cover wrong Store/context/root stop and replay without writes; actual Task Core tests distinguish known cancelled settlement from unknown diagnostics.


`forkSession` 是原主体对 root Session 的具名 `session.create` 因果命令。它在同一短事务核对 Store、原选择、稳定边界和整个执行组的停止资格；活动或未知效果拒绝。省略 boundary 采用当前 selected 高水位，null 为空历史，准确 messageId/seq 采用已选且保持完整 Tool 配对的前缀。大 Model 输出通过持久 toolCallCount 与真实 Tool execution/message 来源核实配对，不从正文预览猜调用。新 root Session 没有原 Run/Execution、owner、审批、grant 或 pending delivery。没有内部 namespacePlan 的直接 Store 调用保持默认省略，回执 omittedExtensionState:true；Runtime 则按可信宿主登记的 copy/rebuild/omit 规则准备完整 namespaceReport，未登记的实际记录默认 omit。标记如实反映报告中是否有省略，没有来源记录时报告为空、omittedExtensionState:false。通用生命周期及原子派生见 [Fork owner](../../../extensions/fork/README.md)，不据此声明所有业务 namespace 已有规则。

复制的历史消息保存 SQL 私有原 message 链，Store 从原创建命令和相同主体核实每个链接、Part 和来源；调用者 JSON 或已知 hash 不能授予跨 Session 读取。Core 在新的明确 Run 中以此证明读取原 Artifact 完整正文，原 scope/Store/subject/Execution 保持不变，不重新绑定 blob 引用或执行原操作。已选且已消费/explicit 的结果仅复制不可变来源引用；未接纳的结果不会自动出现。重复 Fork 返回原回执，selection/边界或 title 改变拒绝。未来 Part 格式按原样保留可读历史，但新的 Model 输入拒绝 fork_content_unsupported，不能把未知格式转换成可执行资格。

[fork.test.ts](../../../../test/isolated/context/fork.test.ts) 使用真实临时 SQLite/Core 和固定 Model，覆盖小正文、≥17MiB 原输出及下一次完整输入、精确配对、原 namespace 省略、真实触发器整体回滚、同 ID 零新事件、原 scope 授权、readonly 重开零 Model/效果、已知失败结果的唯一低信任来源、空/已排除边界、未来格式和实际未知 Job/活动组拒绝。Session rename/delete 由独立管理模块负责；扩展 copy/rebuild 的可信登记和原子派生见 [lifecycle owner](../../../extensions/fork/README.md)。

[压缩 owner](compression.README.md) 维护单选纯算法 slot、同 Loop 的真实 Model 摘要、原范围/Artifact 来源、原子发布与窗口预检 reset；它保留历史及 selection，查询不触发收费。


`readOriginalRunSelection({expectedStoreId, sessionId, subjectId, runId})` 是可信宿主的只读观察，不是 HTTP 或普通 Extension ReadContext 权限。实际原 Run 的 immutable selection pin 和原 Command 的主体、Session、origin Store、input pin 必须相等；当前观察仍核 expectedStoreId，离线恢复保留原 origin，不把历史来源重标为新 Store。

观察返回 `{selection, highWaterSeq}`。selection 来自同 Session 的实际 selection snapshot，核对原 context.select/Fork producer 的请求摘要、闭合回执、边界与 ranges；highWaterSeq 是本次短读事务的 Session 分配水位，不声称冻结旧 Message 正文。历史正文仍由宿主按原 trigger 上界与当前所选分支资格分别验证。producer 曾生成但 snapshot 缺失、未来游标、foreign scope、破坏的 pin/receipt 均拒绝，不用当前选择猜旧选择。

初始 root selection 没有 snapshot；只有原 session.create、原 Run/Command pin 与该 Session 首次 context.select 的实际前序关系能证明 implicit tail0/ranges[]。Fork 初始 selection 必须有实际 Fork receipt 和同 Session snapshot。递归原 selection 证明最多 64 层、1 MiB snapshot metadata、每个 ranges 最多 256；按精确 producer 查询，不设置累计 Session 历史数量额度。方法不写事件、不取得 owner、不启动 Model 或执行工作。

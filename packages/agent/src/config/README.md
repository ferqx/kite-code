# Host configuration and credentials

`deriveMcpSourceReadSet(parentOptions, originalParentReadSet, actualChildOptions)` is a host-only source observation helper. Its caller must first establish the real child activation, carrier, Run, Session and Store relation. The helper independently reads both complete Session scopes, compares the parent read-set exactly with its original capture, and checks Profile/Store/Workspace plus every canonical source identity, ETag, approval/auth binding, finite variables and safe server projection. It returns the actual child read result without changing the parent's Session digest or proof. Same-name servers in another Workspace, scope retagging and byte drift fail locally. This helper grants no Tool, Job or credential permission and performs no vault/transport operation.

`@kite-ai/agent/config` is an explicit host-only leaf. Importing it does not discover files, open locks, read credentials or create a Runtime. Hosts supply new user/Workspace JSONC paths; this leaf does not discover, read or migrate old Kite configuration/data. The current formal clients' legacy settings schema is not this new assembly schema.

`readConfigurationFile({path})` returns `{path,exists,etag,value}`. An absent file has a stable absence ETag and creates no directory or lock. The default bound is 1 MiB, optionally up to 8 MiB. Non-object, malformed, duplicate-key JSONC, non-regular/hardlinked/symlink files and invalid UTF-8 fail locally. Error codes contain no raw file text, backend exception or credentials.

配置数组不再额外按 512 或 4096 项拒绝；实际配置文件字节边界、JSON 深度、对象字段与凭据校验仍适用。完整命名目录按准确 ID 合并并封存，超过单页的目录由宿主公共读取接口分页，不能因默认项目数静默丢项。真实 5001 项 Skill 配置的文件读取、覆盖合并与不可变快照见[配置测试](../../test/isolated/config/config.test.ts)。

`updateConfigurationFile({path,ifMatch,operations})` supports field `set` and `remove` with explicit paths. It takes a short nonblocking stable sibling OS lock (`<path>.lock`), reads the latest bytes, checks their SHA-256 ETag, validates the existing JSONC, applies `jsonc-parser` edits, fsyncs a private temporary file and atomically renames it into place. Unrelated unknown fields and comments are retained where the parser can preserve them; comments attached to removed/replaced syntax cannot always survive. Malformed originals are retained verbatim instead of becoming empty objects. A stale ETag returns `configuration_conflict`; a held OS lock returns `configuration_busy`. Retry requires a fresh read and explicit fresh IfMatch, rather than blindly repeating the edit. File, edit-count, path-depth and JSON shape limits are finite.

The stable lock is not removed on close, so two processes lock the same coordination file across content replacement. POSIX uses native flock. Windows defaults to the fixed native current-user backend. General declarations use host-only `windowsPathPolicy:'scope'` by default, so an ordinary inherited-ACL Workspace is not required to become private; callers reading private Profile configuration choose `'private'`. Both paths reject reparse/irregular/hardlinked objects and read bounded bytes from the actual native handle, with final path identity verification. Workspace locks, temporaries and repair backups remain private, and publication never changes the Workspace directory ACL. MCP Profile source/approval/auth metadata uses the private policy while its raw project declaration uses scope safety. A trusted override cannot bypass the fixed native Store/Worker checks; there is no insecure success fallback. These tests ran on macOS, not Windows release qualification. Scope paths are trusted host inputs; the host controls the canonical parent directory. The leaf rejects a symlink/hardlinked final file and verifies no-follow opened identity. It cannot grant an untrusted client arbitrary filesystem access.

An external editor need not respect the lock. A second byte-digest check immediately before rename detects changes observed before publication, but an editor racing the final check/rename can still overwrite or be overwritten; this is not an atomic filesystem compare-and-swap against arbitrary external writers. `configuration_publication_uncertain` can mean rename succeeded and later durability/read-back failed, so inspect the latest ETag before deciding to write again. JSONC publication and SQLite configuration notifications are separate media, not one transaction.

`resolveConfiguration({defaults,user,workspace,explicit})` applies exactly that precedence. Ordinary top-level values, including arrays and nested objects, replace their predecessor; there is no undefined recursive merge. Only `models`, `tools`, `skills`, and `mcp` arrays have declared named rules: unique `id` per layer, shallow item merge with stable first-seen order, and nested item values such as `options` replace as a whole. `{id,remove:true}` removes an inherited item; a higher layer can explicitly re-add it. `{id,enabled:false}` retains a disabled capability fact that composition must not enable. Removing a user file override reveals the lower-layer default; it does not mutate defaults. An empty named array contributes no items rather than erasing all defaults.

`createConfigurationSnapshot` produces a deeply frozen, independently cloned `{version:1,digest,configuration}`. It projects the supported assembly contract, including model/provider identity, endpoint and complete non-secret options; tool definition versions/options; Skill path/digest/options; MCP transport/command/args/endpoint/options; enabled/disabled state; and credential references. The digest covers this full canonical projection, not just selected IDs. Unsupported fields stay in the original/effective configuration but are not invented execution inputs. A host must use this same supported projection for assembly and save it with the Run, rather than copying arbitrary raw config into history. Changing later configuration cannot mutate an old snapshot. There is no Agent category field or extra execution Loop.

Configuration writes reject recognized credential-body properties, raw header/env maps and endpoint userinfo/query secrets; assembly snapshots reject them in supported options. Credentials belong in the vault, not arbitrary config strings, MCP arguments, model messages or options. Credential refs use opaque `credential:<uuid>` IDs; config is not a secret storage backend.

`createCredentialVault({backend})` explicitly injects `CredentialBackend {kind,put,resolve,remove}`. A reliable OS credential store is preferred. `createOsCredentialBackend({service,accountNamespace,nativeFactory?})` supplies an actual lazy native adapter: only an explicit credential operation imports `@napi-rs/keyring` and constructs an AsyncEntry in the chosen service/account namespace. Injected native factories support bounded adapter testing without touching a keychain. This leaf does not shell out, install system dependencies, select a plaintext-file fallback or read user credentials at startup. macOS/Linux/Windows native storage qualification is pending. Without a backend, only dependent credential operations return `credential_unavailable`; history/SQLite readers do not require a vault. `createTemporaryCredentialBackend()` supplies process-local memory and reports temporary persistence in each returned reference. New backend/process instances cannot retrieve those temporary references.

`put(secret)` returns only an opaque reference and persistence kind. `resolve(ref)` accepts the original reference object or its persisted ID string and returns a private host value for the concrete operation; it is never part of ModelRequest, Command JSON, snapshot, logs, SSE or diagnostics. `revoke(ref)` also accepts the original object or ID string and blocks new and already pending resolution in that vault before attempting backend deletion. Successful deletion makes the backend reference unavailable; a failed delete is reported locally, with the current vault still refusing it. Cross-process persistence/revocation depends on the injected OS backend actually implementing its contract. Already resolved strings or already dispatched remote requests cannot be recalled by deleting a credential, and the API does not claim otherwise.

Evidence: twelve focused tests use actual temporary files, two real Bun processes with stale CAS, a separate real child holding the native OS lock, comment/unknown-field preservation, immutable snapshot digest/options, temporary backend restart loss and revocation during a controlled lookup. Native factory tests verify lazy loading, explicit service/account namespaces, storage/read/removal lifecycle and sanitized failures; they do not claim a real keychain was exercised. `bun test packages/agent/test/isolated/config/config.test.ts` and Agent typecheck verify this bounded foundation. Default Service composition, configuration HTTP routes, reliable OS backend qualification and full client settings migration are separate owner/integration responsibilities.


`inspectConfigurationFile({path})` is a bounded diagnostic read that returns parsed data or `value:null,error:invalid_jsonc` with the exact-byte ETag; it never exposes invalid source text. `repairConfigurationFile({path,ifMatch,value})` is an explicit operation for an existing invalid JSONC object document only. It uses the same stable short lock, exact ETag and final digest recheck as ordinary edits, validates the replacement, preserves the exact original bytes (including any BOM) in a private owner-only `.config-repair-backups` directory, then fsyncs and atomically publishes the valid object. At most 16 backups are retained; reaching the limit is a local failure rather than deleting originals. Valid documents cannot use this replacement path. Only a SHA-256 backup reference is returned to the trusted host; public Service views omit that reference and all backup text. Ordinary updates still reject malformed originals and never silently replace them with `{}`. The same external-editor race and separate filesystem/SQLite durability limits apply.


`updateConfigurationFile` 可接收可信宿主的同步 `validateCandidate` / `validatePublication` 闭包，在目标 OS 短锁内校验已编辑的完整对象、并在发布前核对非目标读取集合。这不是 Runtime、HTTP 或配置文件输入能力；不等待用户或网络、不提供跨文件事务。目标最新 ETag 与原子发布机制保持。Settings 服务使用这些检查拒绝竞争的 user/project 配置；[配置测试](../../test/isolated/config/config.test.ts) 验证目标锁真实持有、非目标编辑导致拒绝且目标原字节保持。

## Private MCP sources and approval metadata

`readMcpSources({profilePath,workspacePath?,scope,variables?,maxBytes?,now?})` 是独立 host leaf。用户源固定为选定 Profile 的 `mcp.json`，项目源固定为实际 canonical Workspace 的 `.kite-code/mcp.json`；没有 home 发现、旧数据迁移、连接、Model 或 vault 端口。可信宿主提供准确 `scope {profileId,storeId,sessionId,workspaceId}` 和无 symlink 的 canonical 根目录。读取不创建目录、文件或锁。文件实际字节限额默认 1 MiB、最高 8 MiB，JSON 深度有限；没有整个 Server 目录的累计项数限额。

返回的 `user/workspace/approvals/bindings/entries` 是冻结的私人事实，包含完整 raw entry 与实际解析后的 transport，不能复制进 Query、Model 或普通 Run snapshot。只有 `registry {revision,servers,errors}` 及安全 `readSet` 可投影：Server 包含稳定摘要 ID、有限显示名、transport 类型、source kind/path digest/root identity、raw/transport 摘要、enabled/source-admitted/reason。这里的 admitted 只表示来源声明、项目批准及认证绑定资格，实际网络/guardian availability、当前 Tool 权限和最后派发许可仍由宿主独立检查。URL、command、args、env、authRef 和 secret body 不进入 registry。非法文件的文本不被公开；解析/路径/字节错误局部化。

源文档保留准确原字节 SHA-256 ETag，拒绝 symlink/hardlink/非普通文件、目录重定向、无效 UTF-8、重复 JSONC key。完整原始条目（包括 unknown 字段、未展开变量、数组顺序）参与 `rawEntryDigest`。实际 URL/command/cwd/args/显式 env/认证声明参与 `transportDigest`。`registry.revision` 另覆盖准确 Store/Session/Profile/Workspace、源 identity/ETags、批准与认证文件 ETags、可信变量供应摘要及有效目录状态。项目同名条目始终遮蔽用户条目，disabled/invalid/pending/rejected 不回退；整个项目源无法解释或不安全时，用户来源也不能借未知项目内容成为 fallback。

变量只识别 `${NAME}`，值来自宿主显式有限、非秘密供应；不读取 ambient `process.env`，不支持 `${NAME:-default}`，不把缺失或空值替换为空串。stdio command/cwd 为绝对路径，args 与显式 env 有限，不继承进程环境；secret/proxy/runtime 注入环境名拒绝。HTTP 原始 headers、userinfo/query/fragment 不装配。认证接受明确 none（省略也无认证）或 opaque Bearer credential；配置中写出 `credential:<uuid>` 自身不授予读取权。OAuth/续期、命名 credential profile、其他 header/scheme 和旧 trust/Tool effects/annotation/retry 声明目前明确 unavailable，原始条目仍私人保留，不隐式降级或转换。

批准文件为 Profile `mcp-approvals.json`，认证绑定为 `mcp-auth-bindings.json`，根对象 unknown 字段与可保留的 JSONC comments 留存。每个 `records` entry 是闭合 schema：共同绑定 `scopeDigest/sourceDigest/serverId/rawEntryDigest/transportDigest`，批准记录另含 approved/rejected；认证记录另含 authProfile、固定 purpose `mcp.http`、opaque vaultRef、expiresAt 和 revoked。原用户 proof 保留 decisionId、Store/Session/Interaction、acceptedRevision、subjectId、requestDigest、recordedAt。读取凭据绑定元数据没有 vault presence lookup。

持久 binding scope 绑定 Profile、Store、canonical Workspace 身份及来源/Server/认证 profile/purpose，不含 Session。同一 Workspace 的后续 Session 可以复用来源批准事实，registry revision 与每次实际执行仍绑定各自原 Session/Run/Execution。保存的原决定 proof 不重标为新 Session，来源批准不等于后续 Tool/credential grant。新 Store、Workspace 同路径替换或来源/实际 transport 漂移不自动承接旧绑定。

`writeMcpSourceMetadata({expectedReadSet,value,validateDecision,afterPublication?})` 只写准确批准/认证元数据；宿主必须通过同步 `validateDecision` 检验真实用户决定，宽权限 allow 不替代此端口。按 canonical 路径顺序同时持有 user/project/approval/binding 的稳定短 OS 锁，在锁内重读完整原 read-set、binding 和决定，临时文件 fsync、0600 原子发布并同步目录。过期 read-set、错误 scope、无效 proof 或原始声明变化在发布前拒绝。发布后的宿主回执失败返回 `mcp_source_publication_unknown`；已发布原 proof 保留，leaf 不重试。文件与 SQLite 不原子，宿主应保存原 HostMutation/Execution ID 并查询原回执。外部编辑者不遵守锁时，最后检查与 rename 之间仍存在真实文件系统 race；不能称为跨介质事务。

Focused [raw-source tests](../../test/isolated/config/mcp-sources.test.ts) 使用真实文件、独立 Bun 进程持有 OS 锁、双进程同 read-set CAS、目录同路径替换、原 source/metadata 漂移、发布后故障和 5001 项目录。它们证明此 leaf 的读取/批准合同；当前没有默认 Service 装配、scoped ordinary source Job、新 OS vault 平台资格、OAuth 或完整编辑界面资格。宿主 Run capture/冷恢复相等及最后 socket/spawn 前检查仍待 Service/MCP owner 集成。

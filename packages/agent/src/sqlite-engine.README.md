# SQLite engine assets

Importing `@kite-ai/agent/sqlite-engine`, parsing its manifest and calling `verifySqliteEngineAsset` do not open a database. The selected binding is loaded during initialization or measurement. The leaf verifies the exact engine identity. The release owner approves the source IDs.

Agent and Service use `node-api:sqlite` with a verified dynamic SQLite library. The binding always applies `SQLITE_OPEN_NOFOLLOW` and preserves the selected connection's filename, statement bindings and transaction behavior. The macOS arm64 release uses the reviewed SQLite dylib. Linux and Windows use their reviewed dynamic library. Installer and maintenance tooling can verify old dynamic or builtin `bun:sqlite` manifests without loading the old runtime.

The compiled package's fixed `storage/engine/` directory contains closed `engine-selection.json` (`{version:1,manifestSha256}`), `engine-manifest.json` and the platform library (`libsqlite3.dylib`, `libsqlite3.so` or `sqlite3.dll`). The manifest pins target, driver, library name, size, SHA-256, exact SQLite version and source ID. Legacy builtin manifests carry `linkage:'builtin'` without library fields. An absent or invalid packaged engine directory fails startup before Profile access. TypeScript source uses the prepared workspace `dist/storage/engine/` and `dist/runtime-native.node`. A source-only isolated runner can explicitly provide an absolute `KITE_DEVELOPMENT_SQLITE_LIBRARY` when the workspace sidecar directory is absent. That selection is unqualified and cannot be promoted into a release selection.

`initializeDefaultSqliteEngine()` runs before public Store Profile access, preflight or Worker creation. An explicitly initialized source host revalidates its original selection. The parent binds the library through `Database.setCustomSQLite` before the first connection. Missing assets, a changed selection and mismatched identity reject. A failed initialization also blocks later default initialization in that module.

The Node-API addon shares the selected native library across Workers in the same process. The private Worker open message carries the parent's exact manifest selection, or null for an isolated unqualified source run. A Worker verifies the manifest and hash, confirms the library path already bound by the parent, and measures its SQLite version and source ID. The Worker does not repeat the setter.

Maintenance's raw source, normalization and UI-validation connections use the same host initializer. Engine selection belongs to the trusted host and its verified package metadata. Node/Electron `node:sqlite` has its own embedded engine and qualification.

Focused qualification uses an owned copy of the existing macOS 3.51.3 library. The relocated Node package measures the exact source in a Worker, opens two public Store Workers for concurrent WAL writes, and exercises backup, restore and cold readonly lookup. Malformed sidecar probes reject before Profile creation. Separate verification probes read old builtin and dynamic metadata. Asset verification is separate from the verified bundle's integrity and use leases.

## 12.2 G0：本地正确性与安全

整体收口时运行：

```bash
bun run test
bun run test:runtime:fault
bun run test:runtime:soak
bun run test:tui:system
bun run typecheck
bun run format:check
bun run lint
bun run check:core-boundary
bun run check:docs-impact
bun run check:docs
git diff --check
```

有状态 PTY journey 在单一 Bun test 内串行执行具名 step；每个 scenario 还显式声明 180 秒外层
timeout，高于默认 165 秒 journey deadline。这样推荐 runner 与裸 `bun test` 直接发现都由 step/journey
边界报告失败，不会先触发 Bun 的 5 秒默认 timeout；裸入口仍不是 Required suite 的替代品。

默认 `bun run test` 在共享进程内串行运行确定性 suite，并为每个进程隔离临时
`HOME`/`KITE_CODE_HOME`。Windows 的真实 ACL、进程身份和平台探测用例使用 30 秒单用例上限；
其他平台保留 Bun 的 5 秒默认值。该差异只覆盖测试外层调度预算，不放宽产品 Runtime 的 deadline。

G0 还要求 Workspace 越界、secret、network、MCP write、destructive/unknown effect 与 Verification
false pass 全部 fail closed；P0/P1 为零；P2 修复或记录处置；安装、卸载和回滚基本流程可用。
`check:core-boundary` 还扫描 `src/` 与 `scripts/`，只允许 `ModelInvocationGatewayV1` import single-attempt
transport，并只允许该 transport 使用 AI SDK `generateText/streamText/generateObject/streamObject` 或底层
LanguageModel dispatch；旧 invoke import 与其他 bypass 都使门禁失败。

Tool Pipeline TP-03 的定向测试对 parent Runtime 的 builtin、MCP、Skill 与 Subagent 外层调用注入
adapter/provider spy，验证无 durable
intent 时零 dispatch、每次 attempt 的 ack 顺序、稳定 idempotency identity、Capability Artifact publish
故障后的 unknown、capability receipt 与 Tool/resource/verification terminal 原子性，以及 restore/reconciliation
不重复调用。真实 PTY journey 还覆盖 MCP auth、只读 Resource 失败继续和 Subagent 人工/自动审批 parity；
这些测试不得通过启用 legacy adapter fallback 获得绿色。

TP-04 继续覆盖 receipt-before-verification：只有真实 `receipt_committed` token 能进入
`verification_planned`，伪造/失败/Artifact publish failure 均不得产生 request；Verification reader 缺失时
reviewer 模型调用数为零。Core boundary fixture 同时证明 Controller 直接导入 concrete Tool/Subagent runner
会失败，而 Pipeline dispatch adapter 的唯一方向可通过。既有 ACORE-EVAL-01 与 20-tool Registry
differential 继续作为 legacy terminal/model-content parity journey。

`tests/evals/agent-tasks/replay-pilot.test.ts` 冻结 RP-02 单 case pilot，不从 CI 生成或修补 baseline。版本控制中
cassette 只含 cassette-local response/tool identity 与 canonical attempt outcome；exact file digest、fixture、
oracle、normalizer、ID/clock revision 和忽略字段都进入 pilot authority。workspace normalizer 当前只投影
terminal/receipt evidence，catalog 仍用完整 `surfaceDigest` 且 `replayDigest=null`；prompt、Tool schema、先前
Tool output 或 fixture binding 任一变化都必须得到 typed replay miss。该测试进入默认发现，但只是 candidate
pilot contract，不是 RP-03 Required gate。

Prompt Contract 的确定性 fixture 使用仓库 tokenizer 计算完整静态 system、cacheable context 和默认内置工具 description/schema；V2 必须不超过同 fixture legacy 的 70%，并输出分项以定位回归。项目指令顺序/大小/链接/写前刷新、phase 工具差异、真实 sandbox、MCP description provenance、Subagent 旧符号清理和 transcript pairing 都有专项测试。

`bun run test:tui:system prompt-contract-v2-production` 使用正常配置显式开启 V2，并以
`NODE_ENV=production` 启动真实 TUI。它从本地 mock Provider 实际收到的 HTTP request 断言包含静态
contract 与 cacheable context 的稳定 System 前缀（adapter 会合并相邻 System frame）、synthetic-user
项目指令、真实用户消息、唯一 Runtime state 和 planning 只读工具面；该测试
属于 production TUI 链路证据，不是公网 Provider 或 release artifact 证据。

`bun run test:first-decision:live` 是唯一的显式 opt-in A/B runner。它固定严格校验的 OpenCode Go route/model，在相同 temperature/fixture 和 1024 output-token 上限下默认每类别各运行十次。`FirstDecisionEvalV1` 明确标记 `first_decision_only`，不能表述为 whole-turn 或 Runtime Journey 结果。runner 按 case/轮次交替 `AB/BA`，输出全局、逐类别和配对结果的计数型脱敏指标，并用预先声明的 5 个百分点不劣界和配对 95% 差异区间返回 `passed | failed | inconclusive`；每个 arm 还必须闭合 model attempt、HTTPS dispatch/response、2xx、usage/token 与唯一 Provider response ID 计数。输出只保留稳定 route alias、credential source 和计数/token 汇总，不保存 ID、完整 endpoint、Prompt、用户/模型正文、实际工具参数或响应内容。无 `KITE_RUN_FIRST_DECISION_EVAL=1` 时报告 `live_eval_skipped`；显式 live 的 route/凭据错误必须失败，不能冒充 dry-run。工具描述的结构、schema、可见性与 recovery 使用确定性 Registry contract 测试，不再为同一工具面维护重复 live fixture。

first-decision CLI 可用 `--output=<path>` 以 `0600` 保存同一脱敏 JSON；其中 `sampleOutcomes` 逐样本记录固定 case/run、AB/BA 位置、工具名、参数是否有效、Planning Shell 的 production effect 分类和固定失败类别，但不保存参数值、Shell 命令或任何正文。Planning 中可证明只读的 Shell 合法，不能仅因工具名为 `shell_execute` 判失败。`bun run test:prompt-cache:live` 则独立验证 V2 Planning/Building 工具 declaration 恒等以及同一 phase 预热后的 Provider cache-read 命中率；目标为 95%，并同时原样报告首次 phase shape 的冷启动命中，不能用稳态数字掩盖首次切换成本。

`tests/evals/tool-journey-v1.test.ts` 是本地 deterministic 整轮证据：scripted model 不能直接制造 terminal/retry/rejection/run.error；10 条 case 的工具执行、durable retry、approval/policy、sandbox fail-closed boundary 与 CompletionGuard 都经过 production Controller/executor/Kernel，再由 reducer/store 状态生成递归 exact-allowlist metadata report。它覆盖 pre-dispatch readiness failure→durable ack→唯一 capability dispatch、`sandbox_error/sandbox_denied`、可触发 fallback sentinel 的零底层调用与 persisted authorization-widening event 零计数、真实 dispatch attempt、typed terminal、recovery lineage/resolution、trusted timing 与 atomic CompletionGuard。环境恢复测试使用 uncached suite，父 reducer/子 provider 对 public stdout/stderr 的八组合共享按 success/failure 分流的唯一投影；shell failure 另有 Runner→Controller→Kernel→provider 的真实双流闭环。该套件不建立真实 Provider 连接，也不产生 HTTP dispatch、usage、唯一 response ID 或 Go usage 证据。

`test:runtime:soak` 的 CI profile 每个固定 case 一次。报告为 `failed` 或 `inconclusive` 时不得包装成
通过。旧 qualification 的 8 轮资源证据只作为按需诊断资产，不是发布后 Task 或必须等待的长期窗口。

```bash

```

`https://opencode.ai/zen/go/v1` endpoint 和 `deepseek-v4-flash`。环境变量和显式本机配置都必须精确

返回思考 token 而没有可验证正文。

## 12.4 TUI 与跨平台原则

默认测试由 `scripts/run-default-tests.ts` 编排，并为每个 test process 使用隔离的临时
`HOME`/`KITE_CODE_HOME`；会直接创建用户级持久数据的定向测试还必须自带临时目录隔离，保证裸跑
单个测试文件也不会写入开发机真实配置或 Session Log。真实 TUI scenario 在单个 runner 内按文件串行运行，具有
单文件 deadline 和 owned process tree cleanup。Required CI 可在独立 runner 间按稳定索引分片，最终门禁要求
全部分片通过；未知/重复 scenario 名 fail closed；teardown 失败不能掩盖测试失败。
PTY 的隔离 HOME 与 workspace 在传入子进程前都解析为 canonical realpath，避免 macOS `/var` 别名把安装私有密钥边界误判为非 canonical；隔离用户配置默认固定 `zh-CN`，使可见文案断言不受 runner locale 影响；验证英文或跟随系统语言的
场景必须显式覆盖用户语言配置，产品默认的设备语言策略不因测试基线而改变。

PTY harness 的 `entryPath` 只允许选择一个测试拥有的 TypeScript composition root，并与 standalone
executable、remote-MCP permit root 互斥。该入口用于验证生产 TUI 生命周期周围的确定性边界：
`sandbox-startup-input` 证明后台 sandbox preparation 不阻塞输入，`cancel-successor-render` 证明取消清理
期间只接受一条 successor、旧 run 不覆盖新 run 状态，并且 live tool progress 持续重绘且不重复消息。

跨平台发行与 effectful execution capability 分开。候选包能安装启动不代表 Shell、writer、MCP write
或 effectful Skill 获得 sandbox 资格；缺少原生隔离时对应 capability 继续关闭。PS-02 的实现验收与
平台资格证据也分开：ADR-0116 规定由 Required GitHub-hosted `macos-15`、`ubuntu-24.04`、
`windows-2025` matrix 生成不可变 evidence/verification artifact；本地非目标 OS、fake/DI、Docker、
WSL、emulation 和 candidate-only diagnostic 都不能替代。当前 head 没有绑定成功 run 时只能记录
`waiting_ci`，verified candidate artifact 也不会自动改变 production support 空集。
绑定 head `28e857f8f41913feee5eacd17a2e61fe6cbb439e` 的
[run 32096568806](https://github.com/ferqx/kite-code/actions/runs/32096568806) 已让三个 Required
native-probe job 通过并上传经 verifier 确认的 artifact，因此 PS-02 的实现与 native fail-closed
evidence 已完成。该绿色矩阵只证明当前负向合约可重现；三平台仍为 `excluded`、
`productionSupported=false`，candidate-only Linux 诊断仍不属于 required evidence。

## 12.5 文档与状态门禁

`check:docs` 会验证 ADR-0069、首发终态 active 规则、全部 Phase 子计划和
`release/oss-first-release/task-status-v2.json`。状态注册表必须精确覆盖 108 个历史 Task：83
`completed`、25 `superseded`、0 optional，没有重复、遗漏或未知 ID。

`check:docs-impact` 按 `docs/documentation-map.json` 判断实现改动是否同步当前文档。提交前必须执行项目
`document-before-commit` skill；文档影响、测试和实现未共同收敛时不得提交或创建 PR。

唯一普通维护者检查清单位于 `release/oss-first-release/MAINTAINER_CHECKLIST.md`。正式 GitHub Release、
npm publish 或其他不可逆公开动作不属于测试流程，必须另行授权。

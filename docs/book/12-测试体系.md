# 第十二章 测试与验证体系

测试以行为边界分层，不维护容易失真的固定用例数量。

## 12.1 测试层次

| 层次 | 目录/示例 | 目标 |
| --- | --- | --- |
| 单元 | `tests/tools.test.ts`、`tests/policies/` | 纯函数、schema、分类和工具行为 |
| Runtime | `tests/runtime/` | Kernel、Scheduler、Reducer、Store、Capability、Verification |
| Runtime 韧性 | `scripts/runtime/run-fault-soak.ts`、`tests/runtime/fault-injection.test.ts` | 固定故障矩阵、恢复不变量、资源趋势和 bounded soak evidence |
| Execution | `tests/execution/` | gateway、permit、circuit breaker、doom loop、reliability |
| 集成 | `runtime/agent.integration.test.ts`、`session-manager.test.ts` | 模型、Runtime、会话组合行为 |
| Golden | `tests/golden/` | 审批、计划、失败恢复、required verification 的事件语义 |
| TUI 组件 | `tests/tui-*.test.*` | reducer、layout、输入、宽字符和渲染稳定性 |
| TUI PTY | `tests/tui-system/scenarios/` | 真实终端进程中的完整交互链路 |

## 12.2 常用命令

```bash
bun run test                     # 默认测试；隔离进程级全局状态 fixture，排除 PTY system suite
bun run test:runtime:fault       # SIGKILL、SQLite 与 fault-soak report contract
bun run test:runtime:soak        # 运行 7-case CI profile；不等同 release qualification
bun run test:tui:system          # 按文件串行 TUI PTY scenarios（单文件硬超时）
bun run test:all                 # 默认测试 + 完整 TUI PTY suite
bun run typecheck
bun run check:core-boundary
bun run check:docs
bun run format:check
```

按改动范围优先运行目标 suite，再运行默认测试。Runtime 架构修改至少覆盖 kernel、scheduler、reducer、store 和相应 golden；MCP/Skill 修改还需覆盖 tool-controller、manager/workflow、policy 和 verification。

`test:runtime:soak` 默认使用 CI profile，每个固定 case 一次并输出版本化报告。Release qualification
至少运行 8 轮；必需资源指标或 descendant PID 检测不完整时结果是 `inconclusive`，不能按通过处理。
报告中的终态覆盖来自真实通过测试的 evidence，不由 case manifest 自动填充；单 attempt 资源增长超限、
持续增长、临时残留、Git worktree registry 差异或进程树残留均会 fail closed。完整契约见
`docs/active/runtime-resilience-qualification.md`。

Fresh Bun process 的 preload before/after 包含模块加载与 JIT 冷启动，只作为诊断并标记
`qualificationEligible: false`；只有 warm-up 后同进程 repeated lifecycle 样本才能进入 release
资源阈值。缺少该稳定态样本时 qualification 为 `inconclusive`。

默认入口由 `scripts/run-default-tests.ts` 编排。绝大多数用例保留在同一个主 suite，并使用 `--max-concurrency=1 --only-failures` 限制 Bun 共享进程中的 test 与输出资源竞争；会临时修改 `process.cwd()` 或 `KITE_CODE_HOME` 的路径解析测试逐文件启动独立进程，不能与依赖这些全局值的 Shell、Plan Artifact 或 Session Logger 测试共享运行时。当前 Ink/Yoga ESM 与 Bun per-file isolate 不兼容，因此不要用 `--isolate` 替代该进程边界。

## 12.3 测试原则

1. 断言可观察行为和不变量，不锁定内部函数调用顺序。
2. Runtime 测试优先检查 Event、State 和 Effect，而不是 UI summary 文本。
3. 外部写入测试必须覆盖 intent、unknown、reconciliation 和禁止盲重放。
4. Required verification 测试必须证明 final 不能绕过门禁。
5. TUI PTY 默认使用真实生产入口和 mock model server，不 mock Ink 渲染主链路。需要成功执行
   远程 MCP 正文调用的场景使用显式测试组合根注入逐 invocation permit；默认生产组合根必须另有
   零请求拒绝场景，不能在共享 harness 中全局放行。
6. 跨平台命令、路径和 sandbox 行为分别验证，不用 Unix 假设覆盖 Windows。

## 12.4 文档与边界检查

`check:docs` 校验文档目录和生命周期；`check:core-boundary` 防止 core 导入 app/TUI。架构行为变化必须同步 `docs/active`，技术全书用于解释当前结构但不高于源码、测试、active 和 ADR。

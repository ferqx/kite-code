# 第十二章 测试与首发验证体系

测试以行为边界分层，不使用企业认证或长期观察替代本地可复现结果。

## 12.1 测试层次

| 层次 | 目录/命令 | 目标 |
| --- | --- | --- |
| 单元与策略 | `tests/` | schema、分类、工具、配置与纯函数 |
| Runtime | `tests/runtime/` | Kernel、Scheduler、Store、Capability、Verification、恢复 |
| Runtime 韧性 | `test:runtime:fault`、`test:runtime:soak` | SIGKILL/SQLite/failure contract 与固定 7-case bounded CI profile |
| Agent/Evaluation | `tests/evals/agent-tasks/`、`tests/evals/capabilities/`、`tests/evals/tool-journey-v1.test.ts` | oracle、核心 adversarial、安全/正确性、false-completion 与 typed ToolOutcome 整轮旅程 |
| Compaction | `tests/evals/compaction/`、`test:model:live` | 结构、事实、语义、continuation、route/handoff 与真实模型兼容 |
| Prompt Contract | `tests/prompts/`、`test:first-decision:live`、`prompt-contract-v2-production` PTY | 分层、工具真实性、token 门禁、production TUI 与 opt-in legacy/V2 first-decision A/B |
| Operations | `tests/observability/`、`scripts/operations/` | metadata-only mapper、status、kill switch、runbook 和本地 rehearsal |
| TUI | `tests/tui-system/harness/`、`tests/tui-system/scenarios/` | 快速 harness 与真实 PTY 完整入口 |
| 开源候选 | `tests/release/oss-*`、`release:*` | standalone build、manifest/checksum、安装、启动、回滚、卸载 |
| 真实 Provider | `test:provider:smoke` | DeepSeek 与 OpenCode Go 各一次低成本最小调用，不记录正文或 credential |

旧 Sigstore/attestation、retained evidence、promotion 和 production supply-chain contract 测试继续存在，
用于证明相关控制面在 authority 为空时 fail closed。它们只是历史安全资产，不属于 ADR-0068/ADR-0069
的发布路线图，也不能在 fixture 通过后产生外部认证结论。

## 12.2 G0：本地正确性与安全

整体收口时运行：

```bash
bun run test
bun run test:runtime:fault
bun run test:runtime:soak
bun run test:tui:system
bun run typecheck
bun run format:check
bun run lint
bun run check:core-boundary
bun run check:docs-impact
bun run check:docs
git diff --check
```

有状态 PTY journey 在单一 Bun test 内串行执行具名 step；每个 scenario 还显式声明 180 秒外层
timeout，高于默认 165 秒 journey deadline。这样推荐 runner 与裸 `bun test` 直接发现都由 step/journey
边界报告失败，不会先触发 Bun 的 5 秒默认 timeout；裸入口仍不是 Required suite 的替代品。

默认 `bun run test` 在共享进程内串行运行确定性 suite，并为每个进程隔离临时
`HOME`/`KITE_CODE_HOME`。Windows 的真实 ACL、进程身份和平台探测用例使用 30 秒单用例上限；
其他平台保留 Bun 的 5 秒默认值。该差异只覆盖测试外层调度预算，不放宽产品 Runtime 的 deadline。

G0 还要求 Workspace 越界、secret、network、MCP write、destructive/unknown effect 与 Verification
false pass 全部 fail closed；P0/P1 为零；P2 修复或记录处置；安装、卸载和回滚基本流程可用。

Prompt Contract 的确定性 fixture 使用仓库 tokenizer 计算完整静态 system、cacheable context 和默认内置工具 description/schema；V2 必须不超过同 fixture legacy 的 70%，并输出分项以定位回归。项目指令顺序/大小/链接/写前刷新、phase 工具差异、真实 sandbox、MCP description provenance、Subagent 旧符号清理和 transcript pairing 都有专项测试。

`bun run test:tui:system prompt-contract-v2-production` 使用正常配置显式开启 V2，并以
`NODE_ENV=production` 启动真实 TUI。它从本地 mock Provider 实际收到的 HTTP request 断言包含静态
contract 与 cacheable context 的稳定 System 前缀（adapter 会合并相邻 System frame）、synthetic-user
项目指令、真实用户消息、唯一 Runtime state 和 planning 只读工具面；该测试
属于 production TUI 链路证据，不是公网 Provider 或 release artifact 证据。

`bun run test:first-decision:live` 是显式 opt-in A/B runner；`test:prompt:live` 仅为兼容别名。它固定严格校验的 OpenCode Go route/model，在相同 temperature/fixture 和 1024 output-token 上限下默认每类别各运行十次。`FirstDecisionEvalV1` 明确标记 `first_decision_only`，不能表述为 whole-turn 或 Runtime Journey 结果。runner 按 case/轮次交替 `AB/BA`，输出全局、逐类别和配对结果的计数型脱敏指标，并用预先声明的 5 个百分点不劣界和配对 95% 差异区间返回 `passed | failed | inconclusive`；每个 arm 还必须闭合 model attempt、HTTPS dispatch/response、2xx、usage/token 与唯一 Provider response ID 计数。输出只保留稳定 route alias、credential source 和计数/token 汇总，不保存 ID、完整 endpoint、Prompt、用户/模型正文、实际工具参数或响应内容。无 `KITE_RUN_FIRST_DECISION_EVAL=1`（兼容旧环境变量）时报告 `live_eval_skipped`；显式 live 的 route/凭据错误必须失败，不能冒充 dry-run。

`tests/evals/tool-journey-v1.test.ts` 是本地 deterministic 整轮证据：scripted model 不能直接制造 terminal/retry/rejection/run.error；10 条 case 的工具执行、durable retry、approval/policy、sandbox fail-closed boundary 与 CompletionGuard 都经过 production Controller/executor/Kernel，再由 reducer/store 状态生成递归 exact-allowlist metadata report。它覆盖 pre-dispatch readiness failure→durable ack→唯一 capability dispatch、`sandbox_error/sandbox_denied`、可触发 fallback sentinel 的零底层调用与 persisted authorization-widening event 零计数、真实 dispatch attempt、typed terminal、recovery lineage/resolution、trusted timing 与 atomic CompletionGuard。环境恢复测试使用 uncached suite，父 reducer/子 provider 对 public stdout/stderr 的八组合共享按 success/failure 分流的唯一投影；shell failure 另有 Runner→Controller→Kernel→provider 的真实双流闭环。该套件不建立真实 Provider 连接，也不产生 HTTP dispatch、usage、唯一 response ID 或 Go usage 证据。

`test:runtime:soak` 的 CI profile 每个固定 case 一次。报告为 `failed` 或 `inconclusive` 时不得包装成
通过。旧 qualification 的 8 轮资源证据只作为按需诊断资产，不是发布后 Task 或必须等待的长期窗口。

## 12.3 G1：普通发布验证

候选构建命令：

```bash
bun run release:build
bun run release:verify
bun run release:smoke
```

build 编译 `kite` 和 `kite-tui` standalone executable；verify 在执行 payload 前检查 exact archive、
manifest、逐文件 SHA-256 和 archive SHA-256；smoke 在临时 managed prefix 中完成 install、CLI help/
version、已安装 standalone TUI 的 version 与真实 PTY startup、第二候选 install、rollback 与 uninstall。

`.github/workflows/release-candidate.yml` 在 `macos-15`、`ubuntu-24.04`、`windows-2025` 原生 runner 上
固定 checkout PR head SHA，验证 manifest commit identity，运行同一流程和 TUI PTY startup，然后上传
14 天保留的 unsigned CI artifact。workflow 只有
`contents: read`，不创建 Release、不 publish、不申请 OIDC/attestation。
候选 TUI startup 是跨平台 executable/PTY smoke，隔离配置中显式关闭 native sandbox，避免自动化代替
用户确认 Windows 一次性 UAC setup；native sandbox、managed identity 与 ACL/Job 能力由 Platform
Capability Probe 的 opt-in E2E 独立验证。

Windows job 在候选构建前固定选择 `1.97.1-x86_64-pc-windows-gnu`，从源码编译
`native/windows-sandbox-runner`。构建必须经过 `build-windows-runner.ts`，把 checkout/Cargo cache
绝对路径映射为固定虚拟路径、固定使用 toolchain 内置 `rust-lld` 并清除 PE 时间戳；再由
`windows-runner-evidence.ts` 重算 runner、isksh 与
Coreutils 摘要并要求 committed pin 零差异。`release:build` 随后把 runner、pin、Shell runtime 和许可证共同写入
`windows-x64` archive；安装/启动/回滚 smoke 与 artifact upload 都消费这个同一归档，不能上传一个
只含 `kite.exe` 而缺少 Windows sandbox runtime 的候选包。

真实 Provider 命令：

```bash
bun run test:provider:smoke -- --provider deepseek
bun run test:provider:smoke -- --provider opencode-go
```

DeepSeek 固定 `deepseek-v4-flash` 与官方 endpoint，并显式关闭 thinking 以确保 16-token 预算用于短回复；
OpenCode Go 走 `openai-compatible` adapter，默认使用 `OPENCODE_API_KEY`、
`https://opencode.ai/zen/go/v1` endpoint 和 `deepseek-v4-flash`。环境变量和显式本机配置都必须精确
使用该 endpoint 与模型。二者都只做一次短响应调用。
runner 输出 provider alias、model、duration、usage、非空布尔值和 credential source，不输出 prompt、
response、key、完整 endpoint 或 error response body。credential 缺失和调用失败都是非零退出；mock
只验证 runner contract，不能替代 G1 真实结果。
DeepSeek 限制 16 output tokens；OpenCode Go 的 reasoning 模型限制 128 output tokens，避免最小调用只
返回思考 token 而没有可验证正文。

## 12.4 TUI 与跨平台原则

默认测试由 `scripts/run-default-tests.ts` 编排，并为每个 test process 使用隔离的临时
`HOME`/`KITE_CODE_HOME`；会直接创建用户级持久数据的定向测试还必须自带临时目录隔离，保证裸跑
单个测试文件也不会写入开发机真实配置或 Session Log。真实 TUI scenario 在单个 runner 内按文件串行运行，具有
单文件 deadline 和 owned process tree cleanup。Required CI 可在独立 runner 间按稳定索引分片，最终门禁要求
全部分片通过；未知/重复 scenario 名 fail closed；teardown 失败不能掩盖测试失败。

PTY harness 的 `entryPath` 只允许选择一个测试拥有的 TypeScript composition root，并与 standalone
executable、remote-MCP permit root 互斥。该入口用于验证生产 TUI 生命周期周围的确定性边界：
`sandbox-startup-input` 证明后台 sandbox preparation 不阻塞输入，`cancel-successor-render` 证明取消清理
期间只接受一条 successor、旧 run 不覆盖新 run 状态，并且 live tool progress 持续重绘且不重复消息。

跨平台发行与 effectful execution capability 分开。候选包能安装启动不代表 Shell、writer、MCP write
或 effectful Skill 获得 sandbox 资格；缺少原生隔离时对应 capability 继续关闭。Docker、WSL 或交叉编译
只能做开发预检，不能替代三平台 hosted artifact。

## 12.5 文档与状态门禁

`check:docs` 会验证 ADR-0069、首发终态 active 规则、全部 Phase 子计划和
`release/oss-first-release/task-status-v2.json`。状态注册表必须精确覆盖 108 个历史 Task：83
`completed`、25 `superseded`、0 optional，没有重复、遗漏或未知 ID。

`check:docs-impact` 按 `docs/documentation-map.json` 判断实现改动是否同步当前文档。提交前必须执行项目
`document-before-commit` skill；文档影响、测试和实现未共同收敛时不得提交或创建 PR。

唯一普通维护者检查清单位于 `release/oss-first-release/MAINTAINER_CHECKLIST.md`。正式 GitHub Release、
npm publish 或其他不可逆公开动作不属于测试流程，必须另行授权。

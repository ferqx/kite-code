# 第十章 Runtime 持久化与会话管理

Kite Code 使用 `bun:sqlite` 实现自有 Runtime Event Store。

## 10.1 Event Store

`src/core/runtime/store.ts` 保存：

- `runtime_events`：按 thread 追加的 RuntimeEvent 日志；
- `runtime_snapshots`：带 event position、state revision、checksum、schema version 和 format epoch 的滚动快照；
- named snapshots：用户可见的恢复点；
- `runtime_mcp_egress_nonces`：远程 HTTP MCP permit 的 nonce digest 全库唯一 claim；与
  `mcp.egress_decided` receipt 同事务写入，且不随 session 删除或 rewind 清理，防止有效期内重放；
- `runtime_file_preimages`：`write_file`/`edit_file` 写入前的文件原像和最后一次 Kite
  写入后的内容指纹（ADR-0042 §4），供 `/rewind` 在确认当前内容未被再次修改后恢复到
  检查点状态；同一检查点窗口内按 path 保留最早原像、更新最新后像指纹，随恢复点截断与
  会话删除级联清理，fork 时复制 fork 点之前的行并重映射事件位置；
- session metadata：名称、更新时间、智能命名状态，以及会话绑定的
  `provider + model name` route。新列通过 additive migration 加入，旧数据库保持可恢复；
  route 只保存配置身份，不保存 API key 或 base URL。

事件追加与快照可在同一事务中提交。恢复时加载快照并校验后续事件；损坏、schema 不兼容或不变量失败必须显式暴露，不能静默制造新状态。
包含 `run.completed` 的 batch 在事务提交后与单事件路径一样创建 named snapshot，避免正常
完成的 turn 缺少 `/rewind` 恢复点。

## 10.2 RuntimeState 恢复

快照包含 transcript、plan、tool calls、approvals、capability binding/search、Skill frame、verification、context compaction checkpoint、model invocation evidence、recovery 等事实投影。Invocation、Receipt 和 required Verification 在重启后仍保持约束力。

Runtime schema v25 与 format epoch `kite-runtime-2026-08-18` 标识当前持久格式。RuntimeStore 自身也持有当前 store version 与 epoch marker。打开已有数据库时先以只读连接检查 marker 和目标 snapshot；全部匹配后才建立可写 Store、读取当前事件尾并用 `reduceRuntimeState()` 顺序归约。缺失、错误或损坏格式在任何 schema 写、reducer、Scheduler、Model、Tool 或 Provider dispatch 前返回明确的 format incompatible 错误。v24/旧 epoch 数据不迁移、不重放、不改写，现有数据库与 Artifact 文件也不主动删除或搬移。

当前 event tail 必须从 snapshot event position 严格连续；checksum、不变量、recovery journal、checkpoint 或 receipt 损坏都 fail closed。非终态外部写入仍恢复为 `unknown`，由 reconciliation 或用户决定收敛，不能盲重放。safe-read 自动 retry 的 durable `tool.retry_recorded` 必须先于第二次 Provider dispatch。

## 10.3 Session Logger 存储与迁移

Session Logger 与 Runtime Event Store 分离。`sessionLoggingPolicyV1` 默认开启并只写结构化
allowlist metadata；显式设为 `false` 时 resolved mode 为 `off`，不创建日志目录。
`content` 需要 release artifact 与用户配置双重 opt-in，项目配置不能开启，并永久排除
reasoning、工具/文件/审批/Plan/Sub-agent 正文与 credential。

POSIX 日志目录使用 `0700`、文件使用 `0600`；Windows 使用 owner-only、禁继承 ACL。writer
固定 no-follow descriptor 和目录 identity，拒绝 symlink/reparse point、hardlink 与祖先替换。
每个活动 session 持有绑定 PID/start identity、owner、目录 identity、nonce 和 heartbeat 的
durable lease；正常或失败终止先原子写 terminal marker，再释放匹配 lease。

维护过程受条目与时间预算限制，只有完整扫描后才按最旧优先执行 retention 和总容量回收。
旧 session 先收紧权限；包含未知文件或 link/hardlink 的 session 移入 sessions root 外的
owner-only `sessions-quarantine` 恢复区，不让已隔离数据永久阻断后续容量检查。旧版 root 内
`_quarantine` 首次维护时整体迁出；损坏 lease、未知 root/frontend 条目、扫描不完整或迁移失败
仍让新 writer fail closed。归档的 2026-06-18 全量本地日志计划只保留历史事实，不能恢复为
当前 serializer 或迁移 fallback。

## 10.4 Artifact

| Store | 内容 |
| --- | --- |
| `PlanArtifactStore` | 版本化计划文档及结构摘要 |
| `CapabilityArtifactStore` | MCP/能力的大型结构化结果与验证证据 |
| `ModelArtifactStoreV1` | production Gateway 使用的私有 canonical Model Surface、response 与 Provider options |
| `FilesystemPreimageArtifactStoreV1` | mutation commit 前必须 durable ack 的完整文件原像与 target/operation identity |
| `SandboxPreparationArtifactStoreV1` | allocating sandbox ready ack 与 crash disposal 所需的 private prepared-plan/cleanup evidence |
| `SubagentTaskArtifactStoreV1` | queue-time request 与 Provider/Driver 最终 task 的两个独立 private 分区 |
| `SubagentContinuationArtifactStoreV1` | blocked child 的完整 snapshot、messages、journal 与 blocked tool identity |
| `SubagentLifecycleArtifactStoreV1` | 跨进程恢复所需的 full sealed Provider handle |
| Session Logger | 可观测事件、trace 与分类记录 |

Plan Artifact 的新写入路径为 `~/.kite-code/plans/{taskId}/v{version}.md`：一个 Task 只有一条
不可变版本链，因此 `planId` 继续留在 Artifact metadata 与 Runtime identity，不再增加文件系统目录。
读取只接受这一当前布局和 PlanDocument V2 metadata；历史嵌套布局与 V1 metadata 不迁移、不回退读取。
Artifact
引用带安全路径和大小限制；Verification 通过引用读取受限内容，而不是把大型结果复制进 RuntimeState。

Model Artifact 使用独立的 `~/.kite-code/model-artifacts/{surfaces,responses,provider-options}/` namespace。
production composition 从 owner-only `~/.kite-code/model-artifacts.key` 加载 installation integrity key；只有
尚无历史 Model evidence namespace 时才允许原子创建。既有 Artifact 对应 key 缺失、损坏、权限过宽或
identity 不安全时不得生成替代 key，也不得回退无 evidence dispatch。
外部 ref 只有 keyed opaque ID、kind、keyed integrity identifier 与 byte length，不暴露路径或 raw content
digest。共享 private immutable primitive 在 POSIX 使用 `0700/0600`，在 Windows 应用 owner-only ACL；
写入经 exclusive/no-follow temp、file fsync、atomic rename、回读验证和目录 fsync，读取拒绝 symlink、
hardlink、owner/permission/identity 漂移与 corruption。GC 只接受覆盖 retained session 及全部 fork 的完整
reachability union，先完成 bounded validation scan，再删除超过 minimum retention 的 orphan 和封闭命名
crash residue；不完整/损坏/未知状态不执行任何删除。

Model store 与 Session Logger 没有正文流转关系，也不复用其 retention。TP-03 已让 Capability store 复用
同一个 private immutable storage primitive，但继续使用独立的 `capability-artifacts/results` namespace、
Capability schema 与 keyed opaque ref。新 receipt 只写 format v2；当前 epoch 的 legacy format v1 只有受限
read-only reader，不能成为新写入或 dispatch fallback。Gateway 只把 opaque ref、keyed integrity identifier
与低信息量 admission/resource facts 写入 Runtime Event/State。每次 model attempt intent 在 dispatch 前 ack；
Response Artifact 与
`model.invocation_completed`/purpose terminal/reconciliation batch ack 前，response 不可消费。

所有 Tool adapter attempt 同样先原子持久化 invocation 与 attempt acknowledgement。adapter 结果先写
Capability Artifact，再把 capability receipt、Tool terminal、所需 resource reconciliation 与 verification
request 作为一个 Kernel batch 提交；Runtime-owned suspension 可以先保存
`capability.execution_result_recorded`，但只有后续 action 的 Tool terminal 才能闭合。Artifact publish 失败
或恢复时发现非 suspension 的未终结 attempt 都进入 unknown，禁止无证据自动重放。Session Logger 与 remote
observability 只记录封闭的 capability kind/status，不复制 invocation identity、digest、ref、locator、错误或正文。
Verification reader 必须与 receipt writer 由同一 installation composition 注入；模块级默认 store 已移除，
reader/key/ref/integrity 不可用时不能调用 reviewer 模型或补造 success evidence。

Sandbox preparation 使用独立的 `~/.kite-code/sandbox-preparations/plans/` namespace、
`sandbox_preparation` kind 与 keyed opaque ref。allocating prepare 后、spawn 前，Pipeline 发布严格 canonical
data-first plan，并把 ref、plan/cleanup/command/preparation digest 原子写入
`capability.sandbox_preparation_ready`；原始 argv/env、Windows framed request、runtime path 与 cleanup payload
不进入 Event Store、Session Logger 或 remote observability。Kernel restore 在任何新模型/工具 dispatch 前
交叉验证 Artifact 与 Runtime ready fact，再记录 disposal intent、执行 reconciliation 并提交 disposal receipt；
intent 后、ready 前的崩溃不需要伪造 Artifact，而是从 preparation digest 重建 allocation identity，记录
abandonment intent 后回收并提交 receipt。缺失/损坏/key unavailable 时 fail closed。当前该 namespace 保守保留，不参与 GC；只有补齐 retained
session/fork 的完整 reachability union 和 minimum retention 后才能删除已完成 plan。

Subagent 另用 `subagent-tasks/{requests,tasks}`、`subagent-continuations/continuations` 与
`subagent-lifecycles/handles` private namespace。模型 Task response 在任何 `model.responded/tool.queued` commit
前发布 request，公开 queue 只保存 role 与 opaque ref；dispatch exact hydrate 后，父 attempt ack 再发布最终 task。
Provider prepare严格回读task、发布full sealed handle；Runtime只在 `capability.subagent_*` additive事实中保存
opaque ref、attempt、keyed dispatch intent、observation/cleanup ordinal，ready ack后才activate Driver。blocked
snapshot 的公开 suspension 同样只含 ref 与低信息 lineage。v25 只接受 private ref，不再读取 legacy raw
queue/suspension；正文、raw digest 与 full handle 不进入 Event Store、Session Logger 或
remote observability。任一key/ref/canonical/owner/cursor交叉验证失败都在模型、Provider或tool I/O前fail closed。

completed invocation 在 restore/fork 时严格读取并交叉验证 Surface/Response route 与 invocation identity；
Artifact missing/corrupt 或 key unavailable 时保留已确认 transcript，但持久化 evidence unavailable 并禁止
strict replay。prepared 且没有 attempt ack 的调用以 undispatched 收敛；已有 attempt ack 无 completion
receipt 的调用及 reservation 收敛为 unknown，不自动重发。`modelInvocations` 是 schema v25 的必需投影；
字段缺失属于 corruption，不归一为空表，也不反推历史 Surface。
RP-01 Evaluation replay catalog 是独立 synthetic 内容域，只按 opaque Surface/Envelope/Outcome digest
匹配，不读取或复制 Production Model Artifact。RP-02 的独立 end-to-end deterministic pilot 仍是
candidate-only；RP-03 另以受审查 manifest 将它与五条 risk contract 聚合成 approved evaluation suite，
Required CI 只做 keyless replay。该 gate 不能用 replay 补造历史调用，也不能从 Production Model Artifact
导出 cassette 或改变 production Source。

Filesystem preimage 使用独立的
`~/.kite-code/filesystem-preimages/preimages/` namespace、`filesystem_preimage` kind 和严格 canonical
payload，继续复用 owner-only private immutable primitive 与 installation integrity key 的 domain
separation。payload 绑定 invocation、operation digest、target identity digest 与完整 preimage；公开 ref 只有
keyed opaque ID、kind、keyed integrity identifier 和 byte length。Tool Pipeline 先完成零写入 prepare，再写
Artifact；只有 Artifact ref 与 operation/target/preimage identity 被
`capability.filesystem_mutation_ready` 精确 durable ack 后，才签发 single-use commit grant。Artifact/key/ack
失败保持零 commit；旧 `runtime_file_preimages` 仅为 rewind 的 best-effort 次级投影，不授权 Provider。

成功 filesystem terminal 只把 digest-only observation 放入 capability invocation state。Event Store、
Session Logger 与 remote observability 不保存 path、正文、grant 或 preimage；mutation-ready 也不进入
Session Logger。rename 后终态证据未知时 Runtime 以 unknown/reconciliation 收敛且不重放。该 store 与状态
投影没有切换 Runtime format epoch。PS-02 已把同一 intent/ready/recovery 纪律扩展到 Sandbox
preparation 与 Runtime-owned process dispatch，并由绑定当前 head 的三平台 GitHub Actions 负向证据完成验收。
这不会把任一当前 unavailable/unsupported backend 提升为 production support，Runtime format epoch 仍未切换。

## 10.5 SessionManager

TUI 的 `SessionManager` 管理多个 `SessionRuntime`：创建、切换、运行、取消、后台缓冲和清理。每个 thread 有独立 Runtime、AbortController、审批、临时 binding 与 `AgentConfig`。普通模型调用、上下文投影和压缩都读取该会话的配置；切换或恢复会话时从 Runtime Store 还原 route。新会话使用当前用户级默认 route，已有会话之间不共享可变的模型配置。

TUI 新建或切换会话只改变前台路由，不取消离开会话的当前 turn；后台 run 和 pending approval/Plan review 继续保留，重新切回后再处理。只有显式取消会先持久化终止事实并触发 AbortSignal。公共 Runtime AbortSignal 同样必须先持久化取消事实，旧 generator 完成清理前，同一 thread 的新任务必须等待，不能与旧 loop 共同访问 Runtime Store。

方案审核通过时，`SessionRuntime` 从持久化 `plan.approved.executionMode` 更新本会话的
`interactionMode` 镜像。TUI 会话快照保存该镜像，后台事件缓冲和历史 RuntimeEvent 回放使用
同一来源恢复它，确保 Footer、权限选择器与下一轮会话参数不会退回审批前模式；后续显式
`interaction_mode.changed` 按事件顺序覆盖该值。

`/compact` 的本地预检拒绝会在当前 TUI 显示命令和终态提示，但不会写入 Runtime Event Store；因此恢复会话时不会把被拒绝的控制命令重放为历史用户消息。通过预检的命令仍以 `user.command_invoked` 持久化，用于审计与恢复后的展示，且始终不进入模型 transcript。

## 10.6 Restore 与 Fork

Restore 将同一 thread 回到 named snapshot；Fork 从选定恢复点创建新 thread。二者由 Runtime Store 执行，不复制未持久化 UI 状态。Fork 会复制选中点及其之前的 named snapshots，并把恢复点与文件原像的 event position 重映射到新 thread，使新会话可以继续向更早恢复点 fork。新 thread 不应继承单次 approval、瞬时 capability binding 或运行中 Effect lease。

自动 named snapshot 只在 `turn.completed` 落盘后创建。Fork 严格解析源事件并保留其时间与
envelope metadata；损坏日志在写目标 thread 前失败。新 thread 清除 full access、命令授权、
瞬时 binding/disclosure、Provider session waiver、pending interaction 与活动执行队列，但保留
稳定的已加载 capability 和历史 invocation 事实。

若选中 snapshot 或其之前将被复制的任一 named snapshot 仍持有未完成的 sandbox preparation/ready/disposal
或 abandonment cleanup authority，Fork 必须在写入 target thread 前拒绝复制该 recovery point。cleanup authority
继续唯一属于 source thread；不能靠清空活动队列或瞬时 binding 把 pending resource 复制到 fork，也不能让两个
thread 竞争同一个 supervisor/runtime handle。cleanup failure 记录为同一 lifecycle intent 下的 pending attempt 与
last failure；后续 recovery 每次至多新增一次 attempt，不重新 prepare/spawn，成功 receipt 才 completed。

Subagent fork使用同类但独立的authority gate：current或将复制的named snapshot只要仍处于dispatch intent、
handle ready、observed-but-not-cleaned或cleanup pending，就在写target前拒绝。startup在新模型/Driver前回读private
handle，对same-process prepared/active handle执行一次bounded abandon/cancel/settle，对cross-process handle只有在
sealed process-start identity证明owner死亡后才确认cleanup；未确认保持unknown/hard block且不重复start/resume。
cleanup-confirmed fork可继续，但target会移除private handle authority，source保留审计事实。

SQLite 在 Windows 使用 `DELETE` journal mode，其他平台使用 WAL，并统一设置 5000 ms busy timeout 支持多会话并发；每个连接在 journal/schema 写入前先安装该 timeout，使初始化与事件写竞争都受同一有界等待约束。Windows 选择 `DELETE` 是为了避开 Bun 关闭连接后仍可能持有 WAL 文件锁的问题。SessionManager 仍需序列化同一 thread 的冲突操作。

## 10.7 Observability 不是持久化 Store

生产 metric reporter 只使用有界内存 queue，不写 SQLite、Session Logger 或磁盘 spool。exporter
失败只关闭诊断通道，不改变 Runtime Event/State；consent 撤回立即清空未发送 queue。Session Logger
policy、remote telemetry consent 和 Provider consent 分别解析，互不隐含。

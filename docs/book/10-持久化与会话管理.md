# 第十章 Runtime 持久化与会话管理

Kite Code 使用 `bun:sqlite` 实现自有 Runtime Event Store。

## 10.1 Event Store

`src/core/runtime/store.ts` 保存：

- `runtime_events`：按 thread 追加的 RuntimeEvent 日志；
- `runtime_snapshots`：带 event position、state revision、checksum 和 schema version 的滚动快照；
- named snapshots：用户可见的恢复点；
- `runtime_mcp_egress_nonces`：远程 HTTP MCP permit 的 nonce digest 全库唯一 claim；与
  `mcp.egress_decided` receipt 同事务写入，且不随 session 删除或 rewind 清理，防止有效期内重放；
- `runtime_file_preimages`：`write_file`/`edit_file` 写入前的文件原像和最后一次 Kite
  写入后的内容指纹（ADR-0042 §4），供 `/rewind` 在确认当前内容未被再次修改后恢复到
  检查点状态；同一检查点窗口内按 path 保留最早原像、更新最新后像指纹，随恢复点截断与
  会话删除级联清理，fork 时复制 fork 点之前的行并重映射事件位置；
- session metadata：名称、更新时间、智能命名状态，以及会话绑定的
  `provider + model name` route。新列通过 additive migration 加入，旧数据库保持可恢复；
  route 只保存配置身份，不保存 API key 或 base URL。

事件追加与快照可在同一事务中提交。恢复时加载快照并校验后续事件；损坏、schema 不兼容或不变量失败必须显式暴露，不能静默制造新状态。
包含 `run.completed` 的 batch 在事务提交后与单事件路径一样创建 named snapshot，避免正常
完成的 turn 缺少 `/rewind` 恢复点。

## 10.2 RuntimeState 恢复

快照包含 transcript、plan、tool calls、approvals、capability binding/search、Skill frame、verification、context compaction checkpoint、recovery 等事实投影。Invocation、Receipt 和 required Verification 在重启后仍保持约束力。

当前 Runtime schema v23 的 `context` 状态只保存 checkpoint-v1 active checkpoint、手动 pending compaction、最近失败、有界历史与 correctness block；瞬时 preflight、请求环境 digest 和 Effect lease 不进入状态。旧 `autoGuard`/`autoGuardV2` 在恢复时剥离，历史 auto pending/effect 不重新调度。恢复按 snapshot event position 重放严格连续的 event tail：只有手动 pending request 时匹配的 completed/failed 才能收敛，同一 completed 已在 snapshot 中时不会重复激活或追加历史。历史 checkpoint-v2 只经 bounded reader 校验并降级为 checkpoint-v1，后续 snapshot 不再写回 v2。Checkpoint 必须通过版本、边界身份、digest、非空 narrative 与 token 缩减校验；损坏的 active checkpoint 被移除并形成 `unrecoverable_checkpoint` correctness block，不能静默投影。Active checkpoint 不删除原始 transcript，manual reset 后可直接回退到完整历史。Correctness block 只有 reason/digest 精确匹配的恢复事件能清除。PSMC-03..06 的 Checkpoint Working Set 与新 boundary 尚未实施；Session Memory 已延期为独立增强，不进入当前 schema。

非终态外部写入恢复为 `unknown`，由 reconciliation 或用户决策收敛，不能自动盲重放。

Runtime schema v18 增加 run-scoped `ResourceBudgetV1` ledger。预算配置、reservation、
dispatch、reconcile、release 和 unknown 都是 Runtime Event，并与下一状态快照原子提交。父子
Agent 不持有私有余额；active/unknown reservation 的 executable upper bound 与已 reconciliation
的 actual usage 共同受同一累计上限约束。v17 及更早 snapshot 只迁移为
`legacy_unconfigured` 标记，不能在恢复中的 production run 热补余额或自动重放外部调用。

Runtime schema v19 保留 v18 ledger，并新增 durable FIFO waiter、`nextWaiterSequence` 和
`RunTerminalOutcomeV1`。Waiter 的 enqueue/promote/cancel/timeout 与 reservation transition
一样进入 event + snapshot transaction；顶层调用与 Subagent child tool/shell 使用同一序列和
compound permit 规则，child promotion + reservation 同批持久化，恢复不允许插队。工具/capability terminal facts 与
budget reconcile 同批提交；crash 后 `reserved` 可证明未 dispatch 才 release，
`dispatch_started` 则转 unknown 并保守占用 upper bound。v18→v19 migration 只补空 queue 和
terminal 可选字段，不重置已有余额。

Runtime schema v20 保留 v19 的预算、FIFO waiter 与 terminal 字段，并给 Tool Call 增加 durable
network admission decisions。每个 allow/deny hop 先以 `network.admission_decided` 提交，再允许
获准 socket dispatch；receipt digest 使 replay 幂等。v19→v20 migration 只升级 schema 并保留
现有调用，不为旧调用虚构 receipt。

Runtime schema v21 继续保留上述事实，并给 Tool Call 增加脱敏 `mcp.egress_decided` decision。
获准的 remote content dispatch 必须先把 nonce digest 和 receipt 原子持久化；全库唯一冲突会
回滚 admitted event，再保存 `permit_replayed` denial。receipt 只保存 route/参数/nonce digest、
permit expiry 和稳定原因，不保存原始参数、正文或 nonce。v20→v21 migration 不补造历史决定。

Runtime schema v22 保留 v21 全部事实，并加入全工具 verified terminal、prepared primary evidence 与 L2
commit/receipt。每个 settled call 必须与唯一 transcript Tool Result、完整 receipt/terminal identity 和
call status/result/message `ok` 三方一致；v22 snapshot 或 event tail 缺失/篡改证明会 quarantine，不能因
feature flag 关闭而按 legacy 放行。v2..v21 的旧 canonical result 只迁移为
`legacy_unverified + legacy_unknown`，`originalEventPosition` 必须来自真实 event prefix；无法唯一证明时
fail closed。

v22 的迁移和普通写入都绑定 `RuntimePersistenceIdentityV1`：snapshot metadata、observed full event head 与
持久单调 generation/fencing token 必须 exact match。rolling v22 snapshot 禁止无 identity `saveSnapshot`；
restore 会交叉验证 metadata/state revision、schema、event cut、prefix revision/event ID/applied event IDs。
rewind、delete/recreate 和 fork-target replacement 都推进 generation，即使 snapshot/head 形成 ABA，旧 Kernel
仍不能重新写入。迁移 candidate 与普通 restore 读取保持零 artifact/snapshot 副作用，只有 Kernel 持有 exact
identity 时才可提交。

L2 reclaim commit 与成功 primary response、resource reconciliation 形成封闭原子分支：无推进固定两事件，
推进固定三事件。commit 只保存 settled range、counts、digests、policy/cache identity，不保存 selected entries
数组或工具正文；restart/resume/fork/reset/rewind 按 durable identity 重建同一 projection。关闭新 flag 不删除
历史 commit/receipt，也不把已验证 terminal 降级。

## 10.3 Session Logger 存储与迁移

Session Logger 与 Runtime Event Store 分离。`sessionLoggingPolicyV1` 默认开启并只写结构化
allowlist metadata；显式设为 `false` 时 resolved mode 为 `off`，不创建日志目录。
`content` 需要 release artifact 与用户配置双重 opt-in，项目配置不能开启，并永久排除
reasoning、工具/文件/审批/Plan/Sub-agent 正文与 credential。

POSIX 日志目录使用 `0700`、文件使用 `0600`；Windows 使用 owner-only、禁继承 ACL。writer
固定 no-follow descriptor 和目录 identity，拒绝 symlink/reparse point、hardlink 与祖先替换。
每个活动 session 持有绑定 PID/start identity、owner、目录 identity、nonce 和 heartbeat 的
durable lease；正常或失败终止先原子写 terminal marker，再释放匹配 lease。

维护过程受条目与时间预算限制，只有完整扫描后才按最旧优先执行 retention 和总容量回收。
旧 session 先收紧权限；包含未知文件或 link/hardlink 的 session 移入 sessions root 外的
owner-only `sessions-quarantine` 恢复区，不让已隔离数据永久阻断后续容量检查。旧版 root 内
`_quarantine` 首次维护时整体迁出；损坏 lease、未知 root/frontend 条目、扫描不完整或迁移失败
仍让新 writer fail closed。归档的 2026-06-18 全量本地日志计划只保留历史事实，不能恢复为
当前 serializer 或迁移 fallback。

## 10.4 Artifact

| Store | 内容 |
| --- | --- |
| `PlanArtifactStore` | 版本化计划文档及结构摘要 |
| `CapabilityArtifactStore` | MCP/能力的大型结构化结果与验证证据 |
| Session Logger | 可观测事件、trace 与分类记录 |

Artifact 引用带安全路径和大小限制；Verification 通过引用读取受限内容，而不是把大型结果复制进 RuntimeState。

## 10.5 SessionManager

TUI 的 `SessionManager` 管理多个 `SessionRuntime`：创建、切换、运行、取消、后台缓冲和清理。每个 thread 有独立 Runtime、AbortController、审批、临时 binding 与 `AgentConfig`。普通模型调用、上下文投影和压缩都读取该会话的配置；切换或恢复会话时从 Runtime Store 还原 route。新会话使用当前用户级默认 route，已有会话之间不共享可变的模型配置。

TUI 把新建或切换会话视为对离开会话当前 turn 的取消；其他客户端可以采用保留后台运行的导航策略。取消会先持久化终止事实并触发 AbortSignal，旧 generator 完成清理前，同一 thread 的新任务必须等待，不能与旧 loop 共同访问 Runtime Store。

## 10.6 Restore 与 Fork

Restore 将同一 thread 回到 named snapshot；Fork 从选定恢复点创建新 thread。二者由 Runtime Store 执行，不复制未持久化 UI 状态。Fork 会复制选中点及其之前的 named snapshots，并把恢复点与文件原像的 event position 重映射到新 thread，使新会话可以继续向更早恢复点 fork。新 thread 不应继承单次 approval、瞬时 capability binding 或运行中 Effect lease。

自动 named snapshot 只在 `turn.completed` 落盘后创建。Fork 严格解析源事件并保留其时间与
envelope metadata；损坏日志在写目标 thread 前失败。新 thread 清除 full access、命令授权、
瞬时 binding/disclosure、Provider session waiver、pending interaction 与活动执行队列，但保留
稳定的已加载 capability 和历史 invocation 事实。

SQLite 使用 WAL 和 5000 ms busy timeout 支持多会话并发；每个连接在 journal/schema 写入前先安装
该 timeout，使初始化与事件写竞争都受同一有界等待约束。SessionManager 仍需序列化同一 thread 的冲突操作。

## 10.7 Observability 不是持久化 Store

生产 metric reporter 只使用有界内存 queue，不写 SQLite、Session Logger 或磁盘 spool。exporter
失败只关闭诊断通道，不改变 Runtime Event/State；consent 撤回立即清空未发送 queue。Session Logger
policy、remote telemetry consent 和 Provider consent 分别解析，互不隐含。

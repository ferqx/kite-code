# 第十章 Runtime 持久化与会话管理

Kite Code 使用 `bun:sqlite` 实现自有 Runtime Event Store。

## 10.1 Event Store

`src/core/runtime/store.ts` 保存：

- `runtime_events`：按 thread 追加的 RuntimeEvent 日志；
- `runtime_snapshots`：带 event position、state revision、checksum 和 schema version 的滚动快照；
- named snapshots：用户可见的恢复点；
- `runtime_file_preimages`：`write_file`/`edit_file` 写入前的文件原像和最后一次 Kite
  写入后的内容指纹（ADR-0042 §4），供 `/rewind` 在确认当前内容未被再次修改后恢复到
  检查点状态；同一检查点窗口内按 path 保留最早原像、更新最新后像指纹，随恢复点截断与
  会话删除级联清理，fork 时复制 fork 点之前的行并重映射事件位置；
- session metadata：名称、更新时间与智能命名状态。

事件追加与快照可在同一事务中提交。恢复时加载快照并校验后续事件；损坏、schema 不兼容或不变量失败必须显式暴露，不能静默制造新状态。

## 10.2 RuntimeState 恢复

快照包含 transcript、plan、tool calls、approvals、capability binding/search、Skill frame、verification、context compaction checkpoint、recovery 等事实投影。Invocation、Receipt 和 required Verification 在重启后仍保持约束力。

Runtime schema v16 的 `context` 状态只保存 active checkpoint、pending compaction、最近失败、有界历史、correctness block 与自动保护状态；瞬时 preflight、请求环境 digest 和 Effect lease 不进入状态。恢复按 snapshot event position 重放严格连续的 event tail：只有 pending request 时匹配的 completed/failed 才能收敛，同一 completed 已在 snapshot 中时不会重复激活或追加历史。Checkpoint 必须通过版本、边界身份、digest、非空 narrative 与 token 缩减校验；损坏的 active checkpoint 被移除并形成 `unrecoverable_checkpoint` correctness block，不能静默投影。Active checkpoint 不删除原始 transcript，manual reset 后可直接回退到完整历史。Correctness block 只有 reason/digest 精确匹配的恢复事件能清除。

非终态外部写入恢复为 `unknown`，由 reconciliation 或用户决策收敛，不能自动盲重放。

## 10.3 Artifact

| Store | 内容 |
| --- | --- |
| `PlanArtifactStore` | 版本化计划文档及结构摘要 |
| `CapabilityArtifactStore` | MCP/能力的大型结构化结果与验证证据 |
| Session Logger | 可观测事件、trace 与分类记录 |

Artifact 引用带安全路径和大小限制；Verification 通过引用读取受限内容，而不是把大型结果复制进 RuntimeState。

## 10.4 SessionManager

TUI 的 `SessionManager` 管理多个 `SessionRuntime`：创建、切换、运行、取消、后台缓冲和清理。每个 thread 有独立 Runtime、AbortController、审批与临时 binding。

TUI 把新建或切换会话视为对离开会话当前 turn 的取消；其他客户端可以采用保留后台运行的导航策略。取消会先持久化终止事实并触发 AbortSignal，旧 generator 完成清理前，同一 thread 的新任务必须等待，不能与旧 loop 共同访问 Runtime Store。

## 10.5 Restore 与 Fork

Restore 将同一 thread 回到 named snapshot；Fork 从选定恢复点创建新 thread。二者由 Runtime Store 执行，不复制未持久化 UI 状态。Fork 会复制选中点及其之前的 named snapshots，并把恢复点与文件原像的 event position 重映射到新 thread，使新会话可以继续向更早恢复点 fork。新 thread 不应继承单次 approval、瞬时 capability binding 或运行中 Effect lease。

自动 named snapshot 只在 `turn.completed` 落盘后创建。Fork 严格解析源事件并保留其时间与
envelope metadata；损坏日志在写目标 thread 前失败。新 thread 清除 full access、命令授权、
瞬时 binding/disclosure、Provider session waiver、pending interaction 与活动执行队列，但保留
稳定的已加载 capability 和历史 invocation 事实。

SQLite 使用 WAL 和 busy timeout 支持多会话并发；SessionManager 仍需序列化同一 thread 的冲突操作。

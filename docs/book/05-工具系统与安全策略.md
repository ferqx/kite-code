# 第五章 Capability、工具与安全策略

## 5.1 工具不是顶层架构

Builtin Tool、MCP、Skill 和 Subagent 都是 Capability provider。当前模型轮次可见的静态工具声明只从
`createBuiltinToolCatalogProjectionV1(snapshot).toolSet` 投影，dynamic MCP 作为独立 Runtime-issued overlay 合并；执行始终由 Runtime 接管，模型侧工具没有绕过 Runtime 的 `execute` 通道。

当前内置能力包括文件读取与编辑、Shell、内容/文件搜索、MCP Resource、Web Fetch、Plan 操作、用户提问、Subagent、Skill 激活/引用和 capability search。具体集合按模式、feature flag、provider 能力和当前 binding 动态生成，因此不以固定数量作为契约。

工具事实采用结构化 contract：summary、useWhen、真实 returns format/fields，以及必要的 constraints/recovery；legacy 与 V2 description 都由同一事实生成。`projectResult()` 的文本、diff、JSON 或 interrupt 协议必须与声明一致，不能把所有工具虚构成统一 `ok` JSON。context-sensitive schema 在模型投影和调用解析时使用同一个 resolved schema。

V2 保持 phase-stable 的 builtin 声明：Planning 与 Building 都向模型声明 edit/write/shell 和完整 task role schema，以维持 Provider 缓存前缀；动态 Runtime block 和工具描述引导正确选择。真正的 phase 边界由执行网关强制：Planning 只执行可证明只读的能力，写入、非只读 Shell 和不允许的子 Agent 角色返回结构化拒绝。动态 MCP、Skill 和其他 Capability 仍按 binding、feature flag 与 execution surface 决定可见性；稳定声明不等于授权。

## 5.2 执行网关

```text
tool call
  → 解析静态请求或 Runtime-issued binding
  → 参数 schema 校验
  → capability revision 校验
  → 副作用分类
  → mode policy
  → auto review / user approval
  → sandbox / network boundary
  → provider adapter
  → structured result + receipt + Runtime event
```

App Tool coordinator 是唯一 composition adapter。Builtin frozen registry/catalog 是全部 29 个 operation 的
唯一 schema/parser/effects/traits/executor 事实源；dynamic MCP 保持独立 binding/catalog revision。Host 对 exact
prepared binding/request/grant/attempt 做 single-use claim、ack 与 receipt lifecycle，Kernel scheduler 只消费 traits
和治理事实，不读取具体工具名。未知动态工具、过期 binding、schema/effects/revision 漂移或不可解释参数都在
Provider/Executor 前 fail closed；旧 Core controller/executor/registry 与 LegacyRuntimeModule 均已删除，没有 fallback。

Tool Pipeline V1 的 TP-01–TP-04 已把不可变 snapshot/resolve/validate/classify 与 Policy、approval、
auto-review、ask_user、本地 admission 接入 production App Tool coordinator。Builtin、MCP binding 与 Skill
disclosure 都先通过严格 revision/freshness 检查；early terminal 是显式类型分支，不会落入 Provider。
Provider readiness 使用按 provider/route/boundary keyed 的 durable lifecycle 与 waiter ledger，每次可能
建连的 attempt 都先获 RuntimeStore ack；search/discovery 只读 snapshot，不触发 readiness。所有
parent Runtime 的 builtin、MCP、Skill 与 Subagent 外层 adapter 现在都经唯一 dispatch boundary：invocation intent 与 attempt 先
durable ack，结果写入私有不可变 Capability Artifact，capability receipt 与 Tool terminal 再由 Kernel 原子
提交。成功 receipt 再进入不可伪造的 typed verification stage；receipt/reader/key/Artifact 缺失时 reviewer
模型零 dispatch。Concrete Tool/Subagent runner import 由静态门禁限制在 Pipeline dispatch adapter，canonical
Tool terminal projection 已从 Controller 移入 receipt stage。不提供失败时回旧路径的 runtime flag，也不提前
改变 Runtime format epoch。PS-01 已让 child filesystem call 由 parent Runtime 建立 namespaced queue，并递归
执行同一完整 Tool Pipeline；terminal durable 提交后才交回 `BuiltinChildRuntimeDriverV1`。PS-03 已将
child lifecycle 与 observation transport 迁入唯一生产 `LocalSubagentProviderV1`，模型循环和 child tool
仍分别只经 Gateway 与 Tool Pipeline；不存在 parent Runtime 的失败回退路径。private task/continuation/handle
readback、two-phase ready ack、same/cross-process reconcile 与 pending fork gate 已闭合；PS-03 replay propagation
qualification 已通过封闭的 deterministic synthetic in-memory Source、fresh strict catalog、真实 Pipeline/Local
Provider/Driver/Artifact 与 `assertConsumed()` 闭合；真实 model handle 由 transport observer 包装并机械断言
attempt 为零，qualification 不写 package，也不扩大为 production replay。

PS-01 已把五个 Workspace filesystem ToolSpec 收敛为 Provider-neutral operation。Tool Pipeline 只在
invocation/attempt durable ack 后签发 sealed grant：观察进入 `observe`；mutation 固定经过
zero-write `prepareMutation`、私有不可变 preimage Artifact、
`capability.filesystem_mutation_ready` durable ack，再进入 single-use `commitMutation`。Local Provider
是生产唯一 filesystem owner；legacy file/search 和 dispatcher 仅存在于 `tests/helpers/` 差分 oracle，Fake
deny/crash 也不会调用 Local fallback。commit 后 certainty 丢失为 unknown/reconciliation，禁止自动重放。

PS-02 已把 Shell confinement 接到 `SandboxExecutionProviderV1`。Pipeline 在 durable Tool attempt 与 allocating
preparation intent ack 后签发绑定 exact argv/command digest、Workspace、execution boundary、network、资源限制
与 cancellation 的 sealed grant；Local Provider 返回 data-first prepared plan、backend capability evidence 和
cleanup handle，不拥有 Policy、approval、Runtime event/state 或 process spawn。真实 backend usability probe
也只能在 preparation intent ack 后发生。private preparation Artifact 与 ready receipt ack 后，Runtime consumer
才能单次启动已通过 admission 的 backend，并继续负责 timeout、cancel、fixed-deadline bounded output 与完整
descendant cleanup。POSIX control/data roots 分离且只把 data root 暴露给 sandbox；cleanup 按 data→control 顺序
使用 pinned descriptor。restore 对
ready-but-undisposed plan 在新 dispatch 前先记录 disposal intent，再 reconciliation/receipt；intent 后、ready 前
的崩溃则用 preparation digest 确定性定位 allocation，并通过 abandonment intent/receipt 回收。旧 Windows direct
executor 与 ToolSpec 自行裸 Shell fallback 已删除；Fake/Local/backend failure 在 Provider 内全部 fail closed。
App 只在 typed pre-dispatch backend unavailable 且 cleanup receipt 已确认后，把已经过 Policy/approval 与
attempt ack 的同一命令交给 host Shell 一次；这不是 sandbox evidence。Darwin Seatbelt 与 Windows allocating
backend 当前因 descendant containment/handle-relative cleanup 未证明而 unavailable，Linux
bubblewrap 只是尚待 native qualification 的候选；当前 production support set 为空。cleanup failed 保持 pending
并允许下一次 recovery 以递增 attempt 重试一次，成功 receipt 前不释放 authority。本迁移没有 feature flag，
这些迁移任务本身未改变当前格式；生产继续使用 State 25、Store 4 与 epoch `kite-runtime-2026-08-18`。

PS-02 的实现验收与平台能力准入分开：原生资格证据由
`.github/workflows/platform-capability-probe.yml` 的 GitHub-hosted `macos-15`、`ubuntu-24.04`、
`windows-2025` required matrix 提供。没有绑定当前 head 的成功 Actions run 时只能记录
`waiting_ci`；本机非目标 OS、fake/DI、Docker、WSL、emulation 与 candidate-only diagnostic 都不能
伪称 native evidence。即使 artifact verified，也不会自动扩大当前空 production support set。
PS-02 实现证据提交 `28e857f8f41913feee5eacd17a2e61fe6cbb439e` 的
[run 32096568806](https://github.com/ferqx/kite-code/actions/runs/32096568806) 已在三平台完成
required conformance、probe、verifier 和 artifact upload，因此 PS-02 Provider seam 与 native fail-closed
evidence 已闭合。Windows 仍在 preparation ready/dispatch 前拒绝，三平台仍为 `excluded`且
`productionSupported=false`。

App Tool coordinator、Builtin operation 与 Verification 只通过 `McpRuntimeProvider` 访问 MCP capability、脱敏 provider directory、调用和资源读取，不依赖 Supervisor control API、Manager 或 TUI。连接重试与 `/mcp` 状态列表不构成执行授权。

`edit_file` 的先读后改状态按 Runtime actor 隔离。成功 `read_file` terminal receipt 才提交 digest-only
observation；prepare 后将同 actor、同 lexical target 的最新 observation content digest 与 preimage 对比。
Parent、child 和 sibling 不共享 freshness；缺少 committed observation 为 `read_required`，外部修改为
`stale_read`。freshness 随 RuntimeState 恢复，不从 transcript、路径字符串或旧内存 tracker 补造。

MCP Provider 失败使用 `provider_auth_required`、`provider_approval_required`、`provider_unavailable` 和 `provider_capability_changed` 的 typed classification。分类来自 Builtin MCP provider contract，不依赖错误消息正则；它可以给模型明确失败事实，但不会自动批准、登录、重试或复用旧调用。

## 5.3 Policy 分层

| 层 | 作用 |
| --- | --- |
| Effect classification | 判断 filesystem、network、external state 的 read/write/destructive/unknown |
| Mode policy | `accept_edits`、`auto`、`full` 下的交互和审批规则 |
| Approval policy | 形成 auto review 或单次用户审批 |
| Authorization grant | 对特定命令或会话范围授予有限权限 |
| Sandbox | 在获准后落实文件、网络和进程隔离 |

审批与 sandbox 是不同控制层。批准操作不自动关闭 sandbox；sandbox 可用也不代表操作已获授权。
Windows、Linux 与 macOS 的 TUI/CLI 发行兼容性也不等于 effectful execution admission。三平台
分别运行原生 CI；Shell、writer、Skill child 与 local stdio MCP 再按各自 sandbox、process tree
和继承证据独立开放。某项能力被关闭不会把整个平台标成不可运行。
macOS Seatbelt 的当前文件边界在启动前把 Workspace 与 runtime temp 解析为 canonical realpath：
普通写入只允许这两个 root，系统/当前运行时依赖只读，其余 Workspace 外路径、symlink escape
和 protected path 由 OS profile 拒绝。精确 `brokered-git-r1` revision 启用时，Seatbelt 恢复
Workspace `.git` 原生 deny，Linux bubblewrap 同样 mask `.git` 目录或 gitfile；Git metadata
只能由 App 注入的 typed broker 访问。旧 ADR-0070 shell Git 豁免仅保留为切换前的开发
兼容路径，不得进入 production qualification。runtime temp 每次 invocation 独立创建为 `0700`、不授予
executable-map；executor 返回前先请求终止已跟踪 process group，未确认退出时 fail closed 并保留
runtime；确认后才以不跟随 symlink 的物理清理恢复 hostile mode/BSD immutable flag，删除不能确认
时也 fail closed，避免并发或跨 Workspace
复用。`full_access` authorization 也
不能扩大该边界。production caller 在 sandbox 关闭或 backend 缺失时必须 fail closed；裸 Shell
fallback 只保留给尚未进入 production composition root 的开发入口。

同一 path evaluator 也供进程内工具使用，但 ADR-0118 将文件与进程投影分离。文件 read 对任何有效路径
免审，当前受信任 Workspace 内 write 对全部名称 allow；Workspace 外 mutation 在 `accept_edits` 下需要
exact approval，获批后不得被文件 protected name 二次拒绝。Tool Pipeline 使用
`workspace_only | external_read | approved_external`，Local Provider 重验 canonical Workspace、scope 与
no-follow identity；`.git`、`.env`、Agent/MCP 配置和 credential-looking 文件可由文件工具读取/搜索，
`.gitignore` 仅作为查询语义。execute/process 投影仍按 Workspace 外、`.git`、Agent/MCP 配置、credential、
shell profile 和 additional deny roots 求值；内建 identity 保留 ASCII 大小写不敏感匹配与 native sandbox
规则。forked Skill 的文件工具继承同一
run boundary；local stdio MCP 在 transport 创建前以该 evaluator 校验 cwd 与 path-like executable，
并把二者的 canonical identity 交给 factory；sealed transport identity 固定关闭 local stdio，
即使 surface bit 被错误打开也不能构造 child。production surface/evaluator 缺失同样在 builtin
adapter I/O 前拒绝；bare runtime pinning 与 native child inheritance conformance 完成前仍不具备
production admission。Git/worktree typed controller 由 App 单独授权并负责 checkout/worktree
placement；模型本地 Git 能力则使用 ADR-0097 的只读 `gitInspect`
surface。`git_inspect` 只接受 status/diff/log/branch-list 的逐 operation strict schema 与 literal path，在进程前验证
repository/common-dir、Workspace 外 binary identity、hostile config/attributes/replace/grafts 与
protected-path evaluator；无法证明时零 dispatch。stage、commit 与远端 Git 不向模型披露。Shell 遇到绝对路径、nested shell、间接 child 的本地 Git metadata 也返回 `nextCapability=git_inspect`；远端 Git 操作
延期到独立 network/credential 设计，不回退 raw shell。
broker 同时拒绝 `core.excludesFile` 等跨边界 config；`diff` 在执行前验证路径历史与 blob provenance，不能证明未来自 protected 名称/内容时 fail closed。App 以流式 UTF-8 安全 byte ceiling 读取 stdout/stderr，溢出即终止 process tree。

Linux bubblewrap 开发边界同样使用 canonical Workspace：`workspace_write` 投影
rw bind，`read_only` 投影 ro bind，逐 invocation runtime 另行 rw bind。清理 runtime 时
使用只暴露该目录和只读系统工具的独立 mount namespace，不跟随内部 symlink。
这是候选后端加固，不是 Linux production 资格；binary discovery 还必须通过真实 namespace
启动探针，syscall filter 也需要独立 negative conformance。硬 process-tree count 与终止清理是
两个证据轴，成功杀死 descendants 不能冒充数量上限。protected path、syscall filter、硬上限、
child inheritance 和生产入口证据未收敛前，该平台仍为 `excluded`；Windows 无 backend 时同样
稳定排除。

Linux 候选新增 cgroup v2 pids `TasksMax` 包装并由 TUI/foreground CLI 共享 composition root，
但只有 GitHub-hosted Ubuntu 原生探针实际通过后才形成候选 evidence。Docker/WSL2 只作预检；
当前首个 surface 不声明 forked Skill/local stdio MCP，且 descendant-safe allowlist 不可用时直接
fail closed，不能退化为 `allow_all`。

密封执行边界下，进程内 `web_fetch` 使用独立 network controller：精确 host allowlist、实际
DNS 地址和每次 redirect 都重新检查，socket 固定到已批准 IP，allow/deny receipt 在 dispatch
前持久化。该控制只提供 host 级隔离。当前 Shell/Skill descendant 无跨进程 allowlist backend，
所以网络固定关闭。Remote HTTP MCP 已使用逐 invocation transport receipt 和相同的 DNS/private/
allowlist/pinned-address enforcer，但当前 production TUI 没有 receipt controller，因此仍在 Provider
lookup 前拒绝；local stdio 在 native child conformance 前始终排除，而不是回退环境代理或
`allow_all`。

Git/worktree placement authority 位于 App，不属于 Builtin Tool 或 Host。共享 checkout 默认只读；仅用户显式选择的
foreground TUI writer 可直接写当前 checkout。D-09 继续禁止 foreground Headless CLI 写入；后台、
定时、无人值守、并发和委派 writer 必须取得 identity-bound controller worktree，失败时不得回退
共享 checkout。controller 只清理 identity 匹配且 clean 的自有 worktree；dirty、conflict、lock 或
identity drift 全部保留现场，也不自动 push、merge 或删除 branch。

controller 的 review handoff 同时覆盖 tracked binary diff 与 untracked 文件的有界、digest 绑定、
binary-safe 内容记录；symlink、special file、hardlink、超限或采集期间变化都会拒绝。其 Git 子进程
使用最小环境并隔离全局配置/credential/askpass；worktree 以 no-checkout 建立并直接 materialize
有界 regular Git blobs，不执行 smudge/process filter，tracked/info attributes、local filter/include
配置均 fail closed。

执行状态是只读 App 投影，不是授权源。它显示实际 sandbox backend/fallback、filesystem/network/
protected-path、controller worktree 和 capability disabled reasons，但省略 Workspace、host、资源限制
与 qualification proof。只有 CLI `--execution-status` 会投影 production gate；TUI `/permissions`
只打开 interaction mode 选择器，不会从普通配置制造 release boundary。

## 5.4 Shell 与外部副作用

Shell 会结合命令、工作区、网络意图和 action envelope 分类。破坏性命令默认拒绝或要求明确用户决策。MCP 的远端 annotation 不是安全事实；未知、写入和破坏性外部副作用即使在高自主模式下也保持保守审批。

MCP Tool 的 allowlist、denylist 和精确 enabled override 只控制 catalog 可见性。逐 Tool effect、minimum approval 与 retry 进入 descriptor revision；unknown/write/destructive effect 不会因为 `minimumApproval: none` 或高自主模式而跳过用户审批。`safe_read` 仅对 effective read 生效，缺少可信 idempotency key 的写调用不自动重试。

## 5.5 执行结果

工具的人类可读 summary 只是 UI 投影。Runtime 还记录结构化结果、失败分类、副作用、文件变化、外部引用、artifact 和 retry safety。高风险执行随后进入 Verification，而不是以 `ok: true` 直接完成任务。

# 第三章 协议层：跨层契约

`src/protocol/` 定义 App 与 Core 共享的稳定数据契约，不依赖 `src/core/` 或 `src/app/`。协议层描述事实和输入，不包含 UI 组件或执行实现。

## 3.1 协议模块

| 文件 | 职责 |
| --- | --- |
| `events.ts` | 面向 App 的 `AgentEvent`、计划、工具、审批、状态与统计载荷 |
| `actions.ts` | `UserAction` 与 `InterruptPayload` |
| `provider.ts` | `UserInputProvider` 交互接口 |
| `capabilities.ts` | Descriptor、Snapshot、Binding、Invocation、Receipt、Artifact |
| `verification.ts` | Verification mode、spec、check、reviewer 与结果 |
| `subagent.ts` | Subagent 角色和生命周期协议 |
| `git.ts` | Brokered Git 只读操作、能力证据、调用回执与失败码 |

事件种类会随产品演进，架构不依赖固定数量。新增事件应保持可序列化、向前可判别，并由 App reducer 显式处理。

## 3.2 两条事件边界

Kite Code 有两类不同用途的事件：

- `RuntimeEvent` 位于 `src/core/runtime/events.ts`，是 Kernel 的持久事实；
- `AgentEvent` 位于 `src/protocol/events.ts`，是 Core 投影给 CLI/TUI 的展示中立事件。

Runtime Event 不能被 UI 直接修改；Agent Event 也不是 Runtime 的恢复数据源。

`ToolResultPayload.status` 以可选的 `success | error | cancelled | exhausted` 表示执行层终态。
`cancelled` 是已确认取消的展示状态，不能替代 Runtime 对未知副作用或 reconciliation 的 canonical
事实判断。

Shell 的 `tool_progress` 是展示中立的有界进度投影，不保证一次事件只包含一行。
`chunk` 可以用 LF 连接一个展示帧内的多条完整行，`line_count` 记录该批次代表的逻辑行数；
当正文为了固定内存而仅保留尾部时，消费方仍应使用 `line_count` 维护准确的进度统计。
终态 `tool_result` 继续承担权威的 bounded stdout/stderr 结果。

## 3.3 用户动作与中断

`UserAction` 当前覆盖审批、拒绝、文本输入、取消、授权切换和结构化计划审核。`InterruptPayload` 包含：

```text
approval    工具或外部副作用审批
input       ask_user 请求
plan_review 计划批准、修改或取消
```

`UserInputProvider` 是 Core 与前端的交互边界：

```ts
interface UserInputProvider {
  onEvent(event: AgentEvent): void;
  requestAction(payload: InterruptPayload): Promise<UserAction>;
  setup?(): Promise<void>;
  teardown?(): Promise<void>;
}
```

## 3.4 Capability 与 Verification 协议

Capability 的稳定身份是 `capabilityId + revision`；模型可见名称只存在于 turn-scoped binding。`LoadedCapability` 额外记录会话按需加载的身份、revision 与首次加载 turn，恢复后仍需依据当前 descriptor 重新签发 Binding。`ExecutionReceipt` 当前由 `CapabilityInvocationRecord` 表达，供恢复、审计和 Verification 使用。

`CapabilityDescriptor` 将 Runtime 审计用的原始 `description` 与模型可见的可选 `modelDescription` 分离，并通过 `descriptionProvenance` 标记 `builtin`、`user_config`、`approved_project`、`generated` 或 `remote_untrusted` 来源。模型描述只能由 admission 后的清理文本或确定性摘要生成；其内容与 digest 属于 capability revision，变化后旧 Binding 必须失效。旧 snapshot 缺少新增可选字段时按 `generated` 保守回退，不提升信任。

`CapabilitySearchResult` 可以持久化不可执行的 unavailable-provider diagnostic。该项只包含 provider 名称、归一化状态、固定 next action 和可选 diagnostic code，不包含 schema、capability ID、参数或 binding；它与可执行 capability candidate 是不同事实。

MCP Resource Directory 属于 Runtime Provider 的只读快照，不是 `CapabilitySearchResult`、loaded capability 或 turn Binding。客户端内置的资源列表与读取结果通过正常 Tool Result 返回；错误同样必须保持 assistant tool call 与 tool result 成对。

`ToolApprovalPayload` 只承载 Runtime 计算出的命令、风险、预期 effects 与可选授权范围。协议不再传播模型提供的 justification、objective、expected observation、failure strategy 或 suggested prefix rule；`shell_execute` 的审批决策与审计 action 分类均由命令形态和当前授权状态派生。

`VerificationSpecV1` 是版本化、可持久化的验收契约。协议只定义检查内容与结果，不在协议层执行命令、读取文件或调用 MCP。

## 3.5 PlanDocument V2 与完成证据

新写入的 `PlanDocument` 使用 `planSchemaVersion: 2`。该版本与 Plan Artifact 容器的
`artifactFormatVersion` 独立：容器格式当前仍为 1。历史 Plan 缺少 `planSchemaVersion` 时属于 V1，
只允许读取/replay；协议字段保持可选是为了反序列化旧 snapshot/event，不表示新生产者可以省略它。

V2 的持久 identity 是 `planId + version + structuralDigest`。`PlanCompletionEvidenceV1` 只包含四类
metadata reference：verification ID/outcome、terminal tool-call ID/succeeded、skipped step ID/reason code、
unresolved failure/approval kind/reference ID。协议不提供 prompt、工具参数、路径、命令、stdout 或任意错误正文
字段；Core reducer 只接受能够由当前 Runtime state 重新投影得到的 evidence。

CompletionGuard V2 的 `completion.blocked` 与 `run.completed` 同样必须携带完整 `PlanIdentity`；guard version、
identity、稳定 reason code 和 correction attempt 共同构成 replay 校验边界。当前 V2 Plan 不接受缺失 identity、
错 revision/digest 或自报 legacy guard 的完成事件；显式 V1 completion 只保留给受控的历史 snapshot tail replay。

## 3.6 ToolOutcome 与 Subagent recovery 协议

`AgentEvent` 的工具终态可携带展示中立的 `outcomeV1` 投影：固定 status/detail、dispatch 与 effect
certainty、recovery disposition、可信 timing 和低基数 unknown-field observation。App 只消费这些字段，
不得从 stdout、stderr、路径、命令或自由错误反推恢复动作。旧事件缺少该投影时继续按 legacy 兼容显示；
当前生产者必须提供通过 Core 严格语义校验的 envelope。

`SubAgentResult` 与 continuation 协议可携带 Core 私有的 recovery journal，以便父子 Runtime 合并
failure instance、`recoveryOf` 与 attempt ceiling。该字段用于持久化和恢复，不属于模型可见结果：
`task` Tool Result 只投影显式 public DTO，identity key、fingerprint、lineage、execution journal、
exhausted fingerprints 和 continuation 都不得进入 transcript、Session metadata、TUI 或 Provider payload。

`SuspendedSubagentSnapshot.blockedTool.reasonCode` 保存 child 原始的人工审批或 auto-review 路由，
防止并发审批排队、持久化与恢复后降低授权边界。该字段为兼容历史 snapshot 保持可选；当前生产者
必须写入，恢复旧数据时缺失值按人工审批处理。`subagent.approval_deferred` 属于 Core Runtime 的
排队事实，不新增第二个 App interaction，也不代表一次新的 child dispatch。

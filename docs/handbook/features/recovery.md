# 取消、继续与恢复

当前通用 Agent 使用新 Store 与明确恢复申请；不会读取、转换或继续旧用户数据库。`resume` 是原 Session 的后续新任务；原 Run 接续、遗留中断、报告恢复与外部 Job 核实分别使用明确接口，具体边界见下文及[当前进度](../../plans/unified-agent-refactor-v1-progress.md)。

历史、投影和订阅只读。已完成且实际清理结束的执行释放所属资源；未知副作用、未确认停止或缺少原身份的情况保留原因，不从进程消失、重连成功或受理回执推定恢复完成。

取消尝试停止当前执行并等待清理，不能撤销已经发生的文件修改或外部调用。结果未知时应先检查实际状态，再决定继续或重新执行。
客户端等待服务响应超时只表示本次请求没有拿到回执；若请求可能修改状态，应查询原命令回执和当前会话状态，不能因超时直接重发。

继续会话是基于已有历史输入新的任务；打开历史本身不应自动重放旧写操作。恢复点提供的是已保存边界，不是任意可见消息都可回滚。

恢复可以涉及会话、代码或二者，具体入口由客户端提供。分叉保留来源并建立新的继续路径；一次性授权不应自动复制成新会话的永久权限。

通用Agent V1.3开发路径已保留跨Fork的原文件检查点和恢复证据：较早点可核后来未选中操作留下的实际文件状态，成功恢复后的新文件基线仍可用于更早恢复。切换上下文选择不会重标原检查点；目标不在当前分支、文件外改或结果未知时明确拒绝。Web已有文件恢复点目录、只读预览和原恢复状态面板，journal状态与实际执行结果分别展示，不能从目录存在推断恢复许可。

开发 CLI、TUI 和 Native 已提供会话、代码、二者三种恢复范围。会话范围只建立选定历史分支；代码范围经独立审批恢复文件；二者先恢复代码，已知成功后由用户明确继续建立分支。首次提交前保存适用的两步原身份，重开后只查原申请；未知结果不重发、不换命令。代码成功后若文件又被编辑或被后来任务改变，第二步会停止，保留第一步成功与第二步未开始。各客户端的实际窗口和正式入口状态分别核对；只读 Web 继续只展示原点与结果。方案和验收见[统一实施计划](../../plans/unified-agent-refactor-v1.md#135-forkrewind)，实际边界见[Files owner](../../../packages/agent/src/business/file-checkpoints/README.md)。

已保存的文件恢复申请会随受支持的离线备份保存。完整原恢复点、适用的代码与会话申请身份、每一步已确认或未知的状态均保留；恢复生成新 Store 后，旧申请仍属原身份，不自动继续、不换命令、不重做文件。私有记录损坏、容量超限或结构不能核实会明确失败，保留来源数据。备份内容和本地“成功”记录本身不授予第二步执行许可；明确继续“二者”时还须核实原 Code 回执，并重新检查原恢复点的当前文件全部未变。文件后来被编辑或被新任务修改时，保留第一步已成功、第二步未开始的结果。

[TUI 恢复指南](../clients/tui/guides/cancellation-and-recovery.md)说明选择与确认。Web 可展示信息但不提供恢复控制。CLI resume 是继续任务，不能当成与 TUI `/rewind` 相同的代码恢复操作。

发生数据或连接错误时，先按诊断处理，不手工修改正在使用的存储来绕过恢复检查。

普通Action已产生效果、但最终结果未保存时，受理回执不表示工作完成。原事实继续可读；同Session后续普通执行保持等待并提示需要恢复，不能从连接目录ready或换申请ID推定原Action已经结束。查询原申请不重做效果，也不会把缺失结果补成成功。此边界与已确认终态、独立后台Job的监督分别核对，当前实现和实际故障范围见[Agent owner](../../../packages/agent/src/storage/README.md#未提交普通-action-的串行边界)及[进度](../../plans/unified-agent-refactor-v1-progress.md)。

## 旧实现恢复与格式转换（历史）

本段记录旧 App Server 的恢复、Store 9/10/13 与 epoch 转换、预算资金和自动状态校正。它不参与当前新入口，不构成旧用户数据兼容承诺，也不恢复 D17 已退役的累计账本；仍适用的未知效果与准确来源约束需在新 owner 中核对。

桌面和 TUI 在继续操作遇到恢复要求时，先核验持久清理与副作用事实；只有已确认清理且没有未决或未知副作用时自动恢复。桌面错误提示中的“检查恢复”仅核验并恢复允许恢复的会话，成功后重新校准，不自动发送草稿。执行被占用、清理未完成、需要恢复、外部结果未知与存储不可用分别反馈。无法证明旧执行已结束时，保留阻断；检查原执行者及相关外部结果后再处理，不能以租约过期、进程消失或用户接受未知结果替代清理证据。

恢复与发送使用各自命令身份。丢失响应时查询原命令的持久回执；无法查明结果则保持未知，不自动重新提交。仍缺清理证据的历史会话保持有原因的恢复阻断；不能仅因历史 Run 已完成或租约过期而推定可以继续。

Desktop、TUI 和 CLI 使用同一正式会话库。新客户端遇到已验证的旧 Store 9、Store 10 或准确旧 epoch 11 时，启动准备会在维护保护下备份、转换并核对旧会话；原会话 ID、已提交历史和可读结果应在新版本中继续展示。迁移只因使用同一会话库的活动旧进程而等待；可核实使用另一独立数据目录的 Kite 进程和其他 Kite 发行入口的存在不阻止迁移。未验证格式、损坏或无法确认旧写入者已退出时明确阻止启动，保留原件，不生成看似成功的空会话列表。历史读取本身不改库；继续执行还须重新满足原会话的工作区身份与授权。参见[会话连续性实施状态](../../plans/session-store-compatibility-and-continuity.md)。

兼容转换保留已经提交到旧会话库的消息、事件、运行记录和关联资料；尚未发送的草稿或仅在界面显示的流式片段不属于数据库保留承诺。Desktop 草稿只在当前页面进程内按会话保留，TUI 未发送输入也须自行保存。收到结果未知提示时应核对原任务与外部效果，不能通过重发草稿冒充恢复。

启动准备显示检查、维护等待、备份、转换与发布阶段。确认存储被占用时会有界等待并重新检查；转换前可安全取消，发布已提交时须先完成结算。Store 13 等已验证旧格式中的未结算执行权在私有候选转换时改为 `recovery_required`，不伪造清理完成或重放原执行；原数据库保持原样，历史在发布后仍可阅读，继续执行须完成原有恢复核验。旧会话即使没有单独保存执行权记录，或处于已确认清理但仍要求恢复的状态，多来源归并也按单库读取的相同规则处理。候选准备未完成且无法确认为临时失败时，同一版本对未变化的会话数据再次启动会明确阻断，不继续复制大型备份；已提交的发布仍优先接续，修复版本可重新核验原数据。已有恢复资料不会自动删除。权限、损坏、未知格式或无法确认旧写入者已退出时不会自动重试或清空历史。无法核实配套客户端身份、安装清单、父进程或旧进程观测时，启动诊断会分别指出受限原因；用户可以按提示检查安装、从受支持的入口重新启动或保存诊断。CLI/TUI 启动错误只输出脱敏诊断类别、阶段、有限准入原因与格式数字，不输出路径、正文或凭据。

已完成的历史会话若仅残留旧执行权恢复标记，发送新消息时会自动核对持久状态。确认旧轮完成、清理已收尾、没有活跃或未知 Run、没有待确认副作用后，直接在原会话开始新一轮，不要求点击“检查恢复”。历史中已耗尽且明确在派发前被策略拒绝的工具记录保留原样，不被当成仍在执行的工具；真实未决执行仍按上述恢复规则处理。

提交新的执行命令时，Service 自动核验旧执行；读取已有会话只展示持久事实，客户端不推断任务是否已退出。有有效执行租约的会话保留进度；旧执行被隔离后，Service 核对子 Agent 和沙箱资源，追加中断终态并更新旧 Run、工具与子 Agent 卡片。已完成结果保留，未知结果不改成成功且不自动重试。旧轮已经结束的未知调用不再阻塞新轮调度与完成。明确尚未派发、无其他执行资源的孤立旧审批可自动取消；无法证明已收尾的资源或仍可恢复的复杂交互保留恢复状态。恢复失败不能隐藏已有历史。

若旧轮已接受并激活，但进程在执行器调度前退出，且完整持久日志证明没有模型、工具或交互派发，下次继续执行命令核验旧轮时将该轮结算为中断；原命令回执仍可查询，不自动重派。

历史消息中的“正在工作”不作为执行存活依据。即使会话已结束或切换到后续任务，Service 也会在下一次执行命令时核对旧子 Agent：父工具已失败或取消、子执行身份唯一匹配且子执行清理已确认时，补记缺失的终态。已成功的子任务在完成结果和清理记录一致时补记完成，不能因为原进程退出就改成失败。其他工具的沙箱清理仍待处理时，已经有确证的子任务状态也应更新；待清理资源继续保留原有诊断。重复执行命令不会重复追加。客户端只展示服务端结果，不自行把旧消息改成取消；仍在存活的执行不受影响。

旧子 Agent 状态校正后，同一次执行的父工具与子 Agent 不应重复显示为两个独立任务。历史记录足以确认归属时，内部工具及其失败信息归入对应任务；真实记录与执行结果保留，不按显示名称合并不同任务。

独立 Agent 的 `followup_task` 受理后，重启会从持久消息、资金和目标模型证据继续；历史 v1 已准备但尚无派发事实的 `current_turn` 可沿原模型请求恢复，已记录外部尝试而无法确认结果时保持 unknown，不自动重发。来源回执为空只证明受理，目标结果与清理状态须通过 Agent 列表、等待或持久历史观察。`interrupt_agent` 的排队子任务停止也以原子 Session 意图和资金结算为准；仅有停止请求不表示清理已确认。

新受理的后续新 turn 即使在发送方 Run 完成后仍可沿独立子 Run 继续；崩溃恢复从原来源资金、目标 checkpoint 与准确派发事实核验。尚未派发且可证明没有外部尝试时，按具名预派发失败释放备付；已尝试而结果无法确认时保留 unknown 和资金未知状态，不重放工具或模型。旧 v1 会话仍按原期限、单模型、零工具授权回放。初始子 Run 已激活、但原启动 grant 过期后的崩溃恢复尚未完成验证，不能把该窗口显示为已确认继续或清理成功。


## 子 Agent 生命周期

子任务由原持久关系和适用取消域决定生命周期。普通父 Run/Execution 取消沿 attached 边传播，明确 detached 后代不会因此停止；根全停止、删除和本 owner 的 Service shutdown 仍覆盖其执行组及旧来源的后来后代。已完成结果保持，取消请求与实际停止分别展示。父工具卡片结束、服务失联或进程消失不能代替资源停止证明，强杀后的未知结果须显式核实；准确规则见[V1.3 取消域](../../plans/unified-agent-refactor-v1.md#116-detached-的统一含义)和[Task owner](../../../packages/agent/src/extensions/task/README.md)。

以下额度善后只描述旧实现，不成为新 D17 运行条件：对于历史上父任务已由用户取消、子任务仍停在未派发初始状态而父级额度已释放的情况，服务恢复会在核对原取消、释放与子任务无外部尝试的持久证据后补记该子任务的取消结果；即使会话已开始新一轮，也按原 Run 的证据核对。这个善后不会重新运行父任务、再次释放额度或启动子任务；证据不足时仍显示需要恢复。

| 状态 | 含义 |
| --- | --- |
| 创建中 | 子执行身份及派发意图已保存，正在准备运行 |
| 运行中 | 子任务已经开始或从等待恢复执行 |
| 等待中 | 等待用户审批、输入或执行排队，尚未结束 |
| 自动审批中 | 服务已开始执行该子任务的自动审批；仅排入审批队列仍是等待中 |
| 已完成 | 子任务成功结束 |
| 已中断 | 异常退出、超时等导致执行中断，并有相应服务端依据 |
| 已取消 | 取消执行已确认；仅提交取消请求不立即成为此终态 |
| 已失败 | 明确执行错误或创建失败，不能混同于取消或中断 |

继续执行命令核验旧执行时，已确认的终态不会被迟到的开始／等待事件重新打开。旧记录缺少取消依据时，不把中断猜作用户取消；已完成的子任务也不会因父工具随后取消而改为取消。结果未知与待清理事实另行保留，状态展示不意味着可以重放原操作。

## 开发统一 Service 的冷报告恢复

统一开发 Service 为已经持久登记的后台汇报提供显式恢复 API。打开历史、连接服务和读取结果都不会自动恢复。恢复请求固定原会话、原报告和原Store；服务只有在原配置与实现能够准确重建、原来源和当前授权仍有效时，才为该报告创建有来源的新一轮。原父轮次保持完成，原工具不会重新执行。

恢复成功回执只说明该申请已经落定，模型是否完成须查询返回的实际Run。原报告因取消、回退、删除或后来新任务失去资格时不能偷偷续轮；结果仍保留历史。找不到原配置或原实现时明确拒绝，不改用当前默认模型。回执丢失只查询原恢复命令，不能通过换ID重发来猜结果。开发 CLI/TUI/Native 已有显式报告恢复消费者；默认新制品现已支持明确 after_turn Task 的一次报告，required/background 不报告；源码外真实默认 Task 资格见[Service owner](../../../apps/service/README.md#默认-task-的源码外资格)。完整默认冷报告强杀和其他平台仍按实施证据判断。这不提供任意旧任务重试或外部Job核实。


## 开发统一 Service 的外部任务核实

对于保存了原关联、恢复配置和适配器版本的未知 Job，可以显式核实原外部任务。核实只查询已发生的操作，不重新启动，也不恢复原 Run。服务分别记录业务结果与原任务是否已结束；“没有找到”“连接失败”或仅有 PID 消失均不能当成成功或未执行。缺原版本、原关联或可靠查询能力时明确保持不可核实，历史仍可读取。

核实证据另存，原未知结果和已经引用的历史保留。只有原任务结果已知且监督结束，才可解除该 Job 对新执行的阻挡；其他未知任务仍阻挡。旧的待自动汇报结果停止投递，不因核实成功自动插入下一轮、重新运行工具或调用模型。当前开发 CLI 提供显式 `job reconcile`，终端/桌面完整恢复面板和通用 Run 恢复仍未由此完成。


## 开发统一 Service 的原 Run 接续

开发统一 Service 提供显式 API，接续崩溃后仍活动、且持久安全边界可以核实的原根任务。当前覆盖模型尚未派发、完整模型回复后的工具序列和完成判定；原审批与工具身份保留，已完成工具不会重做，已完整回复的模型不会为恢复而重新询问。打开历史、重新连接和读取命令都不会自动接续。

恢复仍须满足原配置、当前授权与来源，并核实取消和上下文选择。半完成初始化、无法确认是否已经产生效果的调用、截断模型结果和暂未支持的子任务边界会明确拒绝，保留原历史；已经结束的 Run 不会重开。恢复申请的受理回执不代表任务完成，响应丢失只查询原申请。开发 CLI 的 `recovery run`、TUI `/recovery` 和 Native 恢复面板显式读取原 Run 后提交；CLI 普通 `resume` 仍是新任务的继续对话。正式旧入口与完整平台资格分别按实施进度记录。

## 开发统一 Service 的遗留任务中断

开发 Native API 提供显式 `session.recover`，中断崩溃后原根会话执行组的遗留任务。仍存活或冻结的原服务持有执行锁时拒绝，不抢占。服务核原 Store、用户主体与准确申请，保存中断、取消和未知执行及未完成回复；原历史保留，不重新调用模型或工具。

可能已经产生外部效果的调用继续显示未知。中断回执不证明这些效果已经停止，也不能靠此操作解除新执行的安全限制；有可靠原适配器时另行核实。响应丢失只查原申请 ID，打开历史和重新连接不自动中断。当前公共 API 与完整终端/桌面恢复消费者的资格分别记录。

开发 CLI/TUI 和 Native 在首次提交前持久保存原恢复申请。进程重开、关闭面板或切换会话后，未确认申请仍保原 Store、Session、目标和命令；用户明确查询原 ID，不自动再提交。Journal 损坏、不可写或满槽时会拒绝新提交并保留原数据。恢复备份生成新 Store 也不把旧申请改绑为新身份。

对可证明尚未派发的原工具，中断会在同一事务保存取消结果及原模型调用配对历史；没有未知效果等阻挡时，可以在原会话输入后续新任务。已经尝试的未知调用继续保留未知，不能因为补齐历史或原命令查回而获得重做资格。

CLI 的 Run/report 恢复落定后继续观察实际返回的原 Run，显示其真实审批或问题，直到完成、失败、取消等终态。等待用户输入和受理成功不能显示为任务完成。Ctrl+C 结束本次观察，不另发业务取消；配对服务与共享服务按各自退出语义处理。当前这些消费者已经过 macOS 隔离开发制品实测，正式安装和其他平台仍待验证。


## 开发统一调用者的普通申请恢复

开发 CLI/TUI 与 Native 在首次发送普通 start、运行中引导、follow-up、原 Command 取消或准确单 Job 停止前，持久保存原完整申请。记录固定原 Store/Workspace/Session、认证 subject、Command ID、准确目标和完整正文摘要，单次 Plan/Workflow envelope 原样保留；原草稿 identity/revision/text 摘要与请求分开。保存失败没有 POST；同一 ID 已存在、应用重开或 prepared/submitting 时未收到回执，都只能查询原 Command GET，不能换 ID 或凭当前活动 Run 补发。

本地记录不是执行权或服务端成功证明。查回核实原 kind、scope、subject、实际 request digest 与对应 Run/target；缺本地记录、原 GET 缺失、错误正文或身份、无法验证时保 unknown。查询不重新执行、不清理后来编辑的草稿或单次 Plan 开关；关闭面板、切会话和取消读取只停止本次读取。取消原 Work 优先固定原 Command，Job stop 冻结准确新鲜 Job，不能借父 Run 或同会话另一 Job。

CLI/TUI 的私有 journal 与 Native 的私有数据库各有明确本地容量：最多 128 条，正文按完整 UTF8 保存，上界 16MiB（CLI/TUI 为整文件，Native 为存储行文本聚合）。容量、损坏或私有存储不可用时拒绝新提交，保留原字节与未确认申请，不驱逐 unknown、不裁正文；这些限制不成为服务端 task quota。只可显式清除已核实 applied/rejected 的原记录。备份恢复生成新 Store 后，原保存意图仍保旧身份，不自动重标或重放。

Native 原申请面板提供原 ID 查询和原完整请求分页读取；状态只显示有限 metadata，完整正文按原 read ID、连续游标、EOF、UTF8 字节数与 SHA 核实。main 保有 profile、token 和存储边界，renderer 不获得它们，也不获得私有执行 authority。普通 IPC 页预算保留，完整 caller 提交具有单独的有限预算；超过预算明确失败，不假装已保存全文。`applied` 只表示原申请回执落定，`cancel_requested` 只表示取消请求受理，实际 Run/Job 终态仍须继续观察。

普通 CLI 操作与真实等待见[命令参考](../cli/commands.md#通用开发入口的持久普通申请)。Native 输入/恢复/profile/模型设置/压缩邻接实测为 37 项、296 条 Bun 断言；随后新增的五种真实 Electron 窗口增量为 5 项、20 条 Bun 断言，另核冷 GET 前后 Core 原 Run/Execution ID 集合不增加。两组证据分别保留，见 [Native owner](../../../apps/desktop/README.md)。窗口涵盖真实 main/preload/renderer、物理 POST/首 GET 丢回应、main/所属 Service SIGKILL、原 Command 一条、完整正文与后来草稿保留。超过 1MiB 的合法 Workflow envelope 在业务中因未配置 skill 被实际拒绝，只证明申请完整与查回链，不证明 Workflow 执行成功。既有 TUI 强杀/PTY 资格独立保留；本片不覆盖正式旧入口切换、Linux/Windows Electron、正式安装或整个 §35。

## Native 原答案的冷查回

Native 在首次发送审批、问题或计划评审答案前保存完整原答案申请。保存失败时不发送；回应丢失或应用退出后，原答案面板只查询同一原命令，不重新回答、不换ID。接受命令不表示决定已接纳；只有准确原答案、目标及决定版本的已保存回执可以确认，身份或结果不能核实时继续未知。

切换会话不会改绑保存答案，查询也不替换当前阅读视图。换Store恢复的旧答案保原来源，关联不可用时不能据此答新卡；旧附件已读证明和审批权限不会随本地记录恢复。原答案随受支持的一致私有数据库备份保存，恢复不执行答案。当前实际双Main窗口与离线资产证据只覆盖本机macOS，正式安装和其他平台范围见[Desktop owner](../../../apps/desktop/README.md)。

## MCP 配置原申请的冷查回

TUI 在首次启用或禁用申请前保存完整原意图。重开同一 Profile 后，当前会话的保存原 ID 仍可从 `/mcp` 列表或详情选择，再显式查询原操作；目录为空、失败或 Server 已移除不影响选择。命令受理、备份内容或本地 phase 都不表示配置已保存，须核实同一原请求的实际回执。未知申请不自动重投，也不被新冲突操作覆盖。

受支持的离线备份保留这些原申请的完整内容与身份，恢复生成新 Store 后不改绑、不执行；原 Store 或主体无法关联时明确不可用。私有存储损坏、不能核实或已达容量时保留原数据并拒绝新提交。实际操作与当前平台范围见[MCP 指南](../clients/tui/guides/mcp-and-skills.md#通用-tui-的-mcp-目录与选择)。

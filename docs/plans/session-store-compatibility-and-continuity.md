# 会话存储兼容性与连续性：V1 最终实施方案

状态：已确认目标的实施设计，尚未实现本方案；不得据此宣称跨版本会话连续性已验收。

日期：2026-09-17。适用：Desktop、TUI、CLI、配套 Service，以及共享同一 Store 的 daemon/Web 读取入口。

本方案取代“版本不兼容时自动切换空 Profile”的处理方向，保留已完成的安全拒绝、有限启动诊断和数据不变验证。此次交付仅为设计与实施文档，不执行迁移、删除数据库或更新程序。

## 1. 产品承诺与边界

**正常使用访问唯一的正式会话数据源。对声明支持的版本变化，程序自动完成兼容或无损转换，保持会话身份、历史、关联和可发现性。不能安全处理时保留当前数据，提供可操作的恢复入口，不切换空库、不丢弃未知数据、不恢复过时备份来冒充兼容成功。**

“唯一”约束的是正式数据源、访问入口和写入权威，不禁止 SQLite 自有 WAL/SHM/事务日志或受控备份。备份不参与正常查询，不接受新写入，不自动成为正式库。显式自动化测试可以使用临时隔离数据；普通开发启动、版本切换和不同客户端不能静默创建另一份用户数据。

数据唯一不等于只有一个 Service 进程：保留现有不同会话可由不同合法 owner 执行的模型，不借本次设计重新引入全局执行 writer。

三项能力分别验收：

| 能力 | 必须满足 |
| --- | --- |
| 读取历史 | 原会话可发现、可打开；内容和关联未丢失；读取失败不能伪装成空历史 |
| 原会话开始新一轮对话 | 沿用原 sessionId；通过当前授权和执行检查后追加消息，不新建替代会话 |
| 恢复未完成 Run | 按持久事实、执行所有权和外部结果确定；不承诺所有旧任务自动续跑 |

不承诺任意已发布旧程序能够理解未来格式，不把“安全拒绝”计为该路径兼容成功。不新增通用迁移平台、长期双写、第二套会话索引、后台格式转换任务或任意数据库自动修复工具。

## 2. 当前事实与缺口

以下来自本次工作树与先前只读审计，不是目标实现：

- 当前 Runtime：schema 10，epoch `kite-session-app-server-2026-09-02`。
- 本机旧 profile：schema 11，epoch `kite-session-accepted-runs-2026-09-15`。相对当前结构，runtime_runs 增加 input_json、preparation_failure_count，调整状态/时间约束并增加待处理输入索引。
- 当前 reader/writer 不维护上述新增 Run 语义；可达 Git 历史未找到 schema 11 的完整实现。当前数据未使用新增字段的先前快照，不等于此后永远不用，更不构成通用降级依据。
- 现有 Store 打开入口先只读预检，支持完整当前结构；已有结构化启动错误、快速退出诊断和正常退出处理。
- 上一轮 epoch source profile 分流让开发程序进入另一份 schema 10 数据。这证明能启动，不能证明旧历史连续。
- 当前文档中的旧 kite.sqlite“保留但不可见”也是需要明确处置的历史入口，不能直接标记为已迁移。
- 已有新建、当前格式重启、拒绝不兼容且字节不变的真实 Desktop 测试；尚无支持版本之间的完整会话守恒证明。

必须补齐：统一数据入口；明确实际支持的格式与路径；跨进程维护协调；经过审计的转换与会话保留验证；启动前恢复交互；Desktop/TUI 跨版本 E2E。

## 3. 格式身份与支持矩阵

### 3.1 分开四种兼容性

应用版本不是 Store schema。数据库结构可读不等于事件/State 可解码，历史可读不等于 writer 可写，Store 可写也不等于客户端和 Service 协议兼容。

保留已有 format_epoch 持久值；不为了统一名字批量重写数据库身份。schema 表示结构演进，epoch 仅表示无法沿用原语义的边界。两者都不能单独触发新建 Profile。

兼容判断必须覆盖：表/索引/约束、State/event schema、Run 状态与输入、receipt 和 Effect 幂等、执行 fencing、Workspace/Fork 关系、Artifact 编码及引用。用户授权不能作为“强制忽略未知格式”的开关。

### 3.2 V1 决策表

| 组合 | 处理 | 是否可以宣称已支持 |
| --- | --- | --- |
| 已验证的原格式读写实现 | 原库直接打开 | 完整 E2E 通过后可以 |
| 已验证来源到目标的无损升级 | 自动进入受控迁移 | 迁移、故障注入和连续性验证通过后可以 |
| 较新格式被较旧 Runtime 打开 | 优先寻找已实现的安全读写能力；其次仅使用经过验证的无损逆转换 | 没有路径就不能声明支持降级 |
| 仅能可靠读取历史 | 只有隔离所有写入口的真实只读组合才允许进入 | V1 不为未证明路径搭建通用只读 Runtime |
| 未知 epoch/schema 或未知事件语义 | 不写入；进入恢复界面 | 不兼容边界通过，不等于兼容能力通过 |
| 无法读取元数据、损坏、权限不足 | 分别诊断，不误标为“只需迁移” | 不尝试用 DDL 修复物理故障 |

支持关系用当前 owner 内少量显式分支/转换函数表达；每条转换有实际源 fixture、明确目标及验证器。不要用 `schema <= current` 或未经证明的 min/max 范围。`migration_required` 只表示存在已实现、可执行的路径；较旧数字本身不证明存在迁移路径。

### 3.3 本机 schema 10／11 的实施决策

先取证 schema 11 的代码/制品来源，并对当前完整 Store 做隔离副本审计。优先补齐目标 Runtime 对确有需求的较新数据语义，再为 schema 10 提供向前转换，避免围绕旧代码删减数据。

不得现在指定“把所有 11 降成 10”，也不得只改 schema/epoch 常量。若无法取得来源，转换只能依据已充分验证的实际布局和事件语义，支持范围明确限定；无法证明的记录必须阻断转换，不能跳过。源格式审计未完成是该路径的实施门禁，其他入口和诊断工作可以独立推进。

旧 kite.sqlite 若确认包含未删除用户会话，也必须列入实际数据处置范围：有明确转换路径才纳入当前库；否则明确报告仍未可访问的历史，本机连续性目标不能标记完成。

## 4. 唯一正式数据入口

### 4.1 正常解析规则

同一 OS 用户的同一 canonical config root，Desktop、TUI、CLI、daemon 使用同一正式 Store 路径；默认路径为该 root 下的 kite-session.sqlite。已有显式数据根选择保留，但必须清楚标明这是另一份用户选择的数据，不能由版本或错误回退隐式触发。

source/installed 的代码位置不决定用户数据位置。撤回 checkout/epoch 自动分流；启动前发现已知历史位置尚未收敛时，不创建空正式库并展示正常首页。无历史位置且确属首次使用时才初始化新库。发现范围限于既有明确路径，不扫描整个 home。

使用既有 canonical/no-follow/owner 检查；持久事实不能仅凭目录名称判断。所有客户端使用同一个 resolver；没有必要不新增 profile registry 或长期 locator 数据库。

### 4.2 已有多目录的一次性收敛

这不是日常迁移分支。先停止相关派发，明确全部候选库的身份与最终提交点，并核对外置资产。

1. 两边一份为空：保留非空数据及其身份，在维护保护下发布至唯一正式位置；空库在验证后才清理。
2. 一份是另一份的完整、可证明子集：以内容与因果关系验证为准，选择保留全部事实的目标；不能只比较条数或修改时间。
3. 两边都有独立新增会话：只有明确的、有 fixture 的合并规则才可转换；sessionId 不重写，所有关联、回执、删除标记和 authority 语义一并核对。
4. 相同身份出现分叉、冲突或来源不明：停止自动合并并报告冲突范围。不能按更新时间覆盖，不能擅自替用户选择丢弃哪份历史。

不要为一般用户新建通用多库合并框架。若当前实际数据不存在第三、四类，实施到有证据需要的范围即可；如果存在，它就是本机收敛的真实阻塞，不能隐去。

目标发布须可恢复：事务内验证目标，目标关闭并确认持久化后才切换入口；跨文件系统不假设 rename 原子。崩溃后能区分已发布目标与未完成暂存，不能重复导入。旧位置在完整验证前不删除，发布后退出所有正常 resolver；保留副本仅作为明确标记的恢复资产。旧程序若仍可写旧位置，则收敛尚未成立，须先解决旧入口准入。

## 5. 迁移所有权与并发

迁移由共享 Service/Store owner 执行，Desktop/TUI 展示进度和恢复操作，不包含 SQL 转换。Kernel 不获得 I/O 或迁移责任。

一个 Session 的执行租约不能代替整个 Store 的维护权限，SQLite 写事务也不能保证一个旧程序在迁移提交后不继续按旧语义写入。

实施要求：所有受支持 Service 在打开 Store 前进入同一维护准入；正常连接持有共享准入，转换需要独占准入直到验证结束、数据库关闭或重新开放。先复用经过证明适用的现有本地锁机制；若不足，新增一个以 canonical 数据源为键的最小跨进程门闩，不能做成协调服务。锁载体不能因删除/重建产生两把锁；OS 崩溃释放行为和 Windows/POSIX 均须实测。

转换前停止新写入和派发，等待已开始操作到达可持久化边界。超时或外部结果未知时进入等待/受限恢复，不伪造清理完成，不强杀无明确归属的进程。只读历史连接也需在 DDL 边界正确关闭或协调。

已持久化的 unknown/waiting 本身不是所有结构迁移的禁令；若转换可以原样保留其事实且没有仍在执行的旧 owner，可转换历史并继续限制该 Run 的执行。不能把要求“外部结果全部已知”变成所有会话历史升级的全局门禁。

未接入维护协议的旧 Service 不能被新锁自动保护。必须证明它已退出，并通过受支持启动入口阻止在迁移期间重新进入；无法证明时不开始迁移。PID 文件、端口空闲或 SQLite 当前没被锁住，都不能单独证明这一点。任意手工启动、绕过准入的历史二进制不纳入跨版本并发兼容承诺。

并发启动只允许一个迁移者；其他客户端显示等待结果，迁移结束后重新只读识别版本，不重复执行转换。

## 6. 自动迁移流程与崩溃恢复

自动只适用于已公布且通过验证的无损路径；不是任意启动读查询的副作用。启动探测、历史查询与 status 保持只读，由专门的启动准备阶段执行转换。

顺序固定为：

1. 只读识别数据源、格式、可执行路径及所需空间；区分权限、锁冲突、损坏、未知格式。
2. 取得维护权；停止相关写入与派发、收尾；再次核实文件身份、格式与版本，防止使用过期探测结果。
3. 从最终已提交快照生成会话保留基线；通过 SQLite 一致性备份机制创建并验证恢复副本，不只复制活跃 WAL 主文件。备份持有时间点、源/目标格式、摘要和受控资产清单；验证副本可独立打开，必要的 journal 规范化只发生在副本，绝不误作用到源。空间不足、备份失败或资产未准备好时不改原库。
4. 在原正式 Store 的事务内执行明确转换。DDL、数据转换及 schema/epoch 更新一起提交；不要提前改版本号。
5. 提交前执行结构、外键、转换语义和会话保留检查。任一失败整体回滚，不按会话跳过。
6. 提交后仍保持维护权，使用目标 reader 重新打开并做应用层验证；成功后才向正常客户端开放。
7. 释放维护权，重新读取目录与原会话，按当前授权开放新一轮对话；旧 Run 另行进入执行恢复判定。

优先单次事务完成实际路径，不实现分批迁移引擎。事务外文件操作不得冒充 SQLite 事务原子性；涉及外置资产时先准备不可变副本并校验、再提交引用，原文件保留至验证结束。确需可恢复文件发布时使用最少的受保护阶段记录，记录只用于该转换，不能成为第二份业务状态。

| 中断点 | 重启后的正确行为 |
| --- | --- |
| 备份前/备份中 | 原库未改；不把未完成备份当作可恢复点 |
| 事务开始后、提交前 | 由 SQLite 恢复事务；重新识别源格式后按同一路径处理 |
| 提交结果未知 | 读取实际 schema 与转换后不变量，不依据进程退出码猜测，不再次盲目转换 |
| 已提交、开放客户端前验证失败 | 保留目标数据和备份，进入维护恢复；不能自动覆盖回旧备份 |
| 已开放且产生新消息后出错 | 保留当前最新数据；重装程序不恢复旧数据快照 |

禁止关闭 journaling/synchronous 来通过性能测试，禁止边迁移边开放写入。具体耗时随数据量显示阶段与活动状态，不承诺固定秒数，也不每次普通启动扫描全部历史。

## 7. 会话保留基线与验证

基线是此次转换的验证输入，在最终一致快照计算；不新增永久会话台账。数量是辅助指标，不能替代集合、内容和关系校验。

| 对象 | 验证要求 |
| --- | --- |
| Session | 未删除 sessionId 集合相同；不替换身份；名称与必要元数据语义保留 |
| 删除事实 | 不复活 tombstone 指向的会话，不误删现存会话；保留相关去重语义 |
| 历史/Event | 身份、顺序、内容、因果和 revision 边界等价；纯结构转换尽量保持原业务字节 |
| Workspace/Fork | 持久归属与来源关系保留；路径变化不重建身份或自动扩大授权 |
| Run/receipt/Effect | 完成不变待执行、未知不变成功；commandId、幂等、顺序与关联保留 |
| Snapshot | 可解码并对应正确历史边界；派生快照仅在有完整可重放历史且已验证重建路径时重建 |
| Artifact/附件 | 内容可读、引用可解析；资产清单覆盖真实外置位置，不能只备份 SQLite 后宣称全部资产已备份 |
| 执行权/恢复 | 保留持久 fencing 和执行事实，不把旧租约复制成新进程有效执行权；恢复沿现有规则重新判定 |
| 客户端投影 | 在同一授权范围内列表可发现、历史可打开；可继续者向原 sessionId 追加 |

语义转换用转换专属验证器证明等价，不能要求所有转换前后字节一致，也不能把“字段被丢弃”作为正常等价。已有损坏或缺失资产需记录原有缺陷；禁止迁移制造新缺失，禁止静默跳过无法验证的保留对象。必要时整体停止并提供诊断。

草稿和未落盘流式片段单独处理：客户端升级关闭前保存已支持的草稿；外部安装器无法触达的运行实例不能被承诺自动保存。明确区分已提交数据、未发送草稿和未知执行结果。

## 8. 列表、历史和执行恢复

Store 不支持时客户端显示存储恢复界面，不渲染“没有会话”的成功态。历史目录接口不得 catch 后丢弃坏记录。

Store 可读但个别会话解码失败时：可靠确认身份与授权后，在既有会话摘要中保留错误入口；不能确认时返回明确的部分加载错误与可重试状态，不暴露未知会话信息。分页必须传播不完整状态，不能把失败页当作空尾页。尽量沿用现有摘要与错误响应，不新建第二份索引。

Workspace 不可达或授权失效时，允许在原有安全范围内读取历史，并提示关联或授权步骤；这不授予工具执行权限。重新认证、选模型与修复 Workspace 不替换 sessionId。

新一轮对话遵循已有 Run 排序和恢复约束；历史可读不代表可以越过未知旧 Effect 直接派发。对未完成 Run 分类为可按既有规则继续、需要用户决定、外部结果未知或暂不支持。迁移不自动批准权限，不重放已完成工具，不写虚假的 waiver、receipt 或 completion。

## 9. 启动交互与恢复出口

Desktop 与 TUI 使用同一套错误原因与处理能力，界面分别呈现；使用现有启动控制链路，无需为了迁移先成功初始化正常业务 Runtime。

结构化诊断最少包含受限错误码、迁移阶段、实际/目标格式版本、是否可重试及当前可执行操作。不要返回任意 stderr、凭据或整条数据库记录。原始错误仅进入受保护诊断；用户界面使用明确说明。

| 状态 | 用户看到什么 | 程序实际能做什么 |
| --- | --- | --- |
| 正在安全转换 | 阶段、已有数据正在保留、取消限制 | 提交前可安全中止；提交期间等待结算，不杀进程冒充取消 |
| 有其他客户端使用 | 哪类实例正在占用及等待状态 | 对自身可确认实例正常收尾；重试准入，不强停外部任务 |
| 空间/权限问题 | 具体原因与所需条件 | 保留原库，条件修复后重试，不切空目录 |
| 未知格式/没有无损路径 | 会话数据仍在，此程序暂不能打开 | 重新检查、保存脱敏诊断、通过已有可靠安装渠道使用兼容版本 |
| 个别记录问题 | 部分加载/原会话读取失败 | 保留入口与原数据；有专属已验证修复器才自动修复 |

不能显示不可执行的“自动修复”按钮。没有可靠更新设施时，不在 V1 临时新增自动下载、任意远端脚本或静默替换程序机制；提供明确的安装/恢复指引和再次打开操作。受支持路径仍必须自动处理，未知路径则允许安全停止，不能把用户无从操作的一句错误当完成。

更新程序版本与恢复旧备份是两件事。重新使用兼容程序应继续打开当前最新 Store，不恢复旧快照。时间点恢复会丢失该时间点后的可见记录，必须明确范围、由用户选择且保留当前最新副本，不能自动覆盖唯一数据。

| 编号 | 场景与关键断言 |

## 13. 发布与完成判定

发布前写明受支持来源/目标格式及最低参与维护协议版本。schema writer、新 reader、迁移器与维护门闩必须在同一合格制品中交付，不能先放出写新格式的版本再补旧数据处理。

程序回滚不自动回滚数据库。已有历史二进制不能被新代码追溯改造；若它不具备未来格式安全拒绝或维护协议，须明确排除其混跑，并在受支持安装入口拦截该组合。

只有以下条件全部成立，才能标记本方案实施完成：

- 唯一正式入口落实，版本变化不会生成另一份正常用户库。
- 实际承诺的路径有实现与验证，未知路径不破坏数据且提供可操作恢复说明。
- 原身份、历史、关联、发现与打开、原会话续聊均通过验收；执行恢复独立且不伪造事实。
- 已知真实历史数据的位置和可访问性已交代，不能以“文件还在”代替完成。
- 故障中断、混合客户端和降级后再升级通过，不丢升级后的新增记录。
- 文档与制品一致，未支持路径和平台明确，不以启动烟测代替迁移资格。

本次文档交付的完成仅指方案与审查，不指上述代码或本机数据处理已经完成。

## 14. 设计审查与资料

过度设计审查：唯一正式入口、跨进程维护、实际转换、会话保留验证和客户端恢复说明为 required；自动 epoch 分流及仅按数字推断可迁移应在实施中移除；通用迁移图、任意版本逆迁移、通用多库合并、自动下载更新器和长期迁移台账为 defer，不搭建空框架。设计结论：按上述边界实施。

SQLite 事务用于原子提交，不能替代业务语义验证；一致性备份是恢复资产，不证明升级后会话可见。参考：[原子提交](https://www.sqlite.org/atomiccommit.html)、[Online Backup API](https://www.sqlite.org/backup.html)、[WAL 与附属文件](https://www.sqlite.org/wal.html)。

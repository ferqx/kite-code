## Summary

`graph.state.plan` is durable runtime state, not ordinary conversation history.
The model still needs to see it in each relevant turn, but the projection should
not be treated as static system instructions.

## Why ToolMessage Is Not Enough

- `update_plan` tool messages are historical evidence, not the current source of
  truth.
- Conversation compaction can drop or truncate old tool messages.
- Multiple `update_plan` calls can leave several historical versions in the
  transcript.
- Builder mode must execute the current persisted plan without inferring it from
  old tool JSON.

The graph state is authoritative. The prompt projection exists only to make that
state visible to the model for the current turn.

## Cache And Provider Considerations

Prefix/KV cache systems generally reward stable leading tokens. Dynamic state in
the middle of the prompt can reduce reuse for everything after it.

System messages are also provider-specific. Some APIs merge, hoist, or separate
system instructions, so dynamic state should not rely on tail `SystemMessage`
semantics.

The provider-friendly shape is:

```text
system(static rules)
system(cacheable runtime context)
...compacted conversation messages
human(synthetic graph.state.plan reminder)
```

The synthetic plan reminder must clearly state that it was generated by the
harness, not by the user. Other tool execution facts should remain ordinary tool
messages unless there is a specific user-facing reason to project them into the
model prompt.
